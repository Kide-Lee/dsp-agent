## 想法一：项目更名为「伊卡洛斯二号」

**原始表述**：项目改名叫伊卡洛斯二号（的英文）。

**说明**：DSP 中玩家驾驶的机甲名为**伊卡洛斯（Icarus）**。"伊卡洛斯二号"即 **Icarus II**，
与想法三（LLM 控制的第二台机甲）同名——项目名与核心玩法指向同一件事，是自洽的。

**待定**：标识符规范与游戏内显示名（见文末待确认清单 Q1）。

## 想法二：LLM 输出受科技约束、并消耗玩家能量

**原始表述**：
> LLM 输出的 TPS 受到升级科技约束，输出时会消耗玩家的能量。

### 已明确

- 输出的**速率（TPS）**不是一个固定值，而是随玩家的科技/升级进度增长。
- 输出**有资源成本**：消耗玩家的能量。

### 技术锚点（已对 0.10.30.3100 的 `Assembly-CSharp` 元数据核实）

| 需求 | 游戏侧锚点 | 备注 |
| --- | --- | --- |
| 消耗能量 | `Mecha.coreEnergy` / `Mecha.coreEnergyCap` | 这就是机甲面板上的核心能量条，扣减后游戏自己的 UI 会实时反映 |
| 能量消耗系数 | `Mecha.energyConsumptionCoef` | 游戏已有"能耗系数"概念，我们的每次输出可以复用它，让升级收益一致 |
| 科技/升级驱动 | `Mecha.coreLevel`（机甲核心等级） | 由科技树解锁上限、再用升级物品提升 |
| 科技进度 | `GameHistoryData`（已解锁科技/升级） | 用于读取"当前科技到哪一步了" |
| 同类能耗参考 | `Mecha.miningPower` / `replicatePower` / `researchPower` / `instantBuildEnergy` | 游戏对每种行为都定了能量单价；我们的"每次输出"按同一套量纲定价才不会突兀 |

**结论：这条想法在技术上是低成本、高契合度的**——能量与等级都是现成的公开字段，不需要新增资源系统。

### 模糊点

1. **TPS 约束作用在"哪里"？** 三种可能，体验差别很大：
   - (a) 约束**聊天文字**的滚出速度 → 玩家直接感受到"AI 在想得慢"；
   - (b) 约束**第二台伊卡洛斯的行动速率** → 聊天不受影响；
   - (c) 两者共用同一个"算力"池。
2. **能量耗尽时怎么办？** 中途截断一句话体验极差。
3. **TPS 的上下限是多少？** 若新档只有 2 token/s，一条 500 token 的回答要等 4 分钟，mod 会被认为坏了。
4. **"升级科技"是复用现有的，还是新增自定义的？** 新增需要打 `LDB.techs` 补丁 + 图标 + 本地化。

### 我的建议（可直接采纳，也可否决）

1. **解耦"生成"与"播放"**：让模型在后台**一次性生成完**（不占用游戏资源），
   再按当前 TPS 允许的速率**在窗口里滴出**，同时按 token 数扣能量。
   → 好处：LLM 的网络延迟与游戏的速率约束互不干扰；"慢"变成一种**刻意的手感**而非卡顿。
2. **TPS 设保底**：即使最低级也给一个可用速度（建议 ≥ 8 token/s），
   让 1 级是"明显慢但能用"，而不是"不可用"。
3. **能量耗尽不截断**：改为**自动暂停并保留上下文**，充能后继续；
   窗口显示"能量不足，已暂停"。绝不半句话截断。
4. **能量单价对齐游戏量纲**：用 `energyConsumptionCoef` 参与计算，
   使得玩家升"能量回路"类升级时，AI 输出的成本也同步下降——与游戏内其他行为一致。
5. **科技先复用后自定义**：M2 先用 `Mecha.coreLevel` 验证手感（零新增内容），
   确认好玩之后再考虑加一条自定义科技线，避免一上来就做 LDB 补丁。

### ⚠️ 一个需要正视的设计张力

**给 AI 加资源成本，会直接抑制玩家使用 AI**——而"多问、多探索"恰恰是本 mod 的核心价值。
如果玩家因为心疼能量而不敢提问，这个功能就自我否定了。

因此我建议：**约束体现在"第二台伊卡洛斯"身上，而聊天问答保持廉价或免费**。
"算力"作为稀缺资源，限制的是 AI **替你做事的吞吐**，而不是 AI **回答你问题的速度**。
这样既保住了游戏性（成长感、资源权衡），又不惩罚提问。

## 想法三：解锁科技后制造第二台伊卡洛斯，由 LLM 控制

**原始表述**：
> 通过解锁某项科技，玩家可以制造第二台伊卡洛斯，该机由 LLM 控制。

### 技术摸底结果（重要）

对 `Mecha` 类的元数据核实显示：

```csharp
class Mecha {
    Player player;          // ← 每台 Mecha 绑定一个 Player
    GameData gameData;
    double coreEnergy, coreEnergyCap;
    ...
    ConstructionModuleComponent constructionModule;
    MechaForge forge;
    MechaLab lab;
}
class Player { Mecha mecha; PlayerController controller; ... }
```

同时**没有发现任何"多机甲"支持**：全程序集里不存在 Mecha 集合类型的字段，
`GameMain.data.mainPlayer` 是唯一玩家，`PlayerController` 直接绑摄像机与输入。

**⇒ 直接 `new Mecha()` 造第二台是不可行的**：它需要一个 `Player`，
而 `Player` 又与摄像机、输入、存档、UI 深度耦合。硬造出来的实例极可能
在存档、渲染或 UI 环节出问题。

### 三条可选路线

| 路线 | 做法 | 风险 | 能力上限 |
| --- | --- | --- | --- |
| **A. 轻量自定义实体**（推荐先验证） | 自己维护一个实体：一个可视化模型（可复用游戏的机甲模型资源）+ 自己实现移动 + 通过游戏的 `PlanetFactory` 建造 API 执行建造 | 中：建造 API 是公开的，但移动/寻路要自己写 | 移动、建造、采矿；**不**参与战斗、不进机甲面板 |
| **B. 复用建设无人机系统** | 让 LLM 调度玩家已有的 `constructionModule`（那本身就是一群会自动飞过去建造的无人机） | 低 | 只是"无人机的自动化"，**不是第二台伊卡洛斯**，与想法有落差 |
| **C. 强行造第二台 Mecha** | 构造 `Player` + `Mecha` 并注册进 `GameData` | **高**：存档格式、渲染、UI、输入全线风险 | 上限最高，但可能做了很久发现走不通 |

**建议**：先做一次**限定时间的可行性验证**（spike），目标是回答两个问题：
1. 能否创建一个**被游戏渲染系统接受**的机甲外观实体（借用 `ModelProto` / 模型资源）？
2. 能否用公开 API 让它在行星上**建造一格建筑**并消耗玩家物品？

这两个问题都能跑通，路线 A 就成立，再谈完整玩法。

### 模糊点

1. **能力范围**：只会移动？会建造？会采矿？会跨行星？会战斗？
   （建议起点极窄：**移动到指定位置 + 建造指定建筑**，先验证乐趣）
2. **资源归属**：用它自己的库存，还是直接消耗玩家背包？
3. **指令方式**：聊天里自然语言（"让二号去北极建 10 个矿机"）？还是专门的指令面板？
4. **存档持久化**：它是游戏实体，**必须能被存档/读档**。DSP 的 mod 存档数据是独立课题，
   这条是隐藏的大工作量，需要单独立项。
5. **能否被摧毁 / 能量耗尽会怎样**？
6. **它是"第二台伊卡洛斯"还是"伊卡洛斯的僚机"**？后者在叙事与实现上都更轻。
