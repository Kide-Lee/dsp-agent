时间：2026-11-01 21:23 左右（Asia/Shanghai）
范围：只做现场勘查与成因分析，未做任何 debug、未改动代码、未清理残留。

## 一、结论摘要

1. 事故可定位到唯一一次会话：存档 `32627157988b1847`（沙盒模式）里的对话 `conv_b01bd7ffb3b241c4`。
2. 该轮 AI 先后写了两个 `run_script` 脚本：
   - 脚本 #1：单次 `game_get_planets`，成功（`calls: 1`、`elapsedMs: 19`）。
   - 脚本 #2：对 10 颗行星循环 `game_get_planet`（`veins: "summary"`），没有任何结果落盘。
3. mod 侧只看到脚本 #1 的那一次 `dsp.call`（`call_5`，`timeout=8000ms`、`elapsed=1ms`，8000ms 是脚本通道的每调用上限，普通 `game_get_planets` 是 20000ms）。
4. 脚本 #2 的第一个 `dsp.call` 在 mod 侧**一条日志都没有**：既没有「开始」，也没有「参数/初始化失败」。
5. 说明进程死在「脚本 #1 的调用结果返回之后、脚本 #2 的第一个调用进入工具分发器之前」这个窗口里。
6. 现场**有残留**，且有一条会直接影响下次启动（孤儿 sidecar 仍占用 8765 端口）。
7. 崩溃本身是原生崩溃，没有托管异常、没有崩溃转储、堆栈无符号，现有证据不足以指认到具体代码行。

### 21:41 补记：崩溃时刻比原先判断的更早

查 `journalctl` 拿到硬时间戳：`21:22:58.233` 报 `wine client error:43c: read: Bad file descriptor`，随后 `21:23:16` 崩溃块落盘、`21:23:28` 结束 overlay。

这意味着：
- 游戏在**脚本 #1 返回后约 0.9 秒**就卡死了，不是「等脚本 #2 到来时才崩」。
- 脚本 #2 是主线程已经死掉 4 秒之后才被模型写出来的，连发送对象都没有。
- 真正需要复现的是**脚本 #1 那一次单独的 `game_get_planets {includeVeins:true}`**。
- 同一次调用在 21:21:56 由模型直接调过（`call_2`，5ms），当时没崩；只有这次经脚本通道（8000ms 超时、`call_5`）之后 0.9 秒出事。
- 所以可疑点从「脚本里的行星循环」收窄为「这一次调用返回后 0.9 秒内游戏侧做的事」：工具结果回传、聊天窗工具块收尾、下一次流式渲染，或这次大 JSON 之后的 GC。
- 崩溃栈顶恰好在 `mono-2.0-bdwgc`（GC/分配路径），与「大结果之后立刻 GC」的形态吻合，但仅凭该栈无法证明。

## 三、现场残留清单

### 3.1 会造成实际影响的残留

**孤儿 sidecar 进程（必须先处理）**

- 进程：`icarus-ii-sidecar.exe`，`pid=848`（`runtime.json` 记录一致）。
- 端口：`127.0.0.1:8765` 仍在 LISTEN；`/health` 返回 `{"status":"ok","version":"1.1.247"}`。
- 原因：游戏是原生崩溃，`OnApplicationQuit` / `SidecarLauncher.Shutdown()` 没机会执行，子进程成了孤儿。
- 影响：下次启动时 `SidecarLauncher.TryPrepare()` 会删掉旧 `runtime.json` 再拉新 sidecar；新 sidecar 绑定 8765 会 `EADDRINUSE`，`startServer` 的 `onError` reject，`index.ts` 打出「127.0.0.1:8765 已被占用；请换端口或先停掉旧的 sidecar」并 `process.exitCode = 1`，mod 侧只能报「sidecar 进程提前退出（exit=1）」。
- 位置：`~/.local/share/Steam/steamapps/compatdata/1366540/pfx/drive_c/users/steamuser/AppData/Roaming/icarus-ii/runtime.json`。
- 已处理（21:43）：用该 prefix 的 Proton wine 执行 `taskkill /F /IM icarus-ii-sidecar.exe`，返回「已强制结束 PID 为 848」，8765 随即释放。
- 旁证：杀掉的同一秒 Steam 的 `console_log.txt` 才写下 `Game process removed`（21:43:54），说明这个孤儿一直吊着 Proton 的启动链，Steam 在这 21 分钟里一直认为游戏还在运行。

**未收尾的会话文件**

- 路径：`.../icarus-ii/sessions/32627157988b1847/2026-11-01T13-21-55-519Z_conv_b01bd7ffb3b241c4.jsonl`。
- 末行是带 `run_script` 的 assistant 消息，没有对应的 `toolResult`。
- 回放是只读的（`agent.ts` 里 `toolSteps` 不回填、不执行），界面不会自动重跑脚本。
- 风险：继续在这个会话里提问时，历史里会带着一个「有 toolCall 无 toolResult」的悬空调用；该项目没有任何会话修复/清洗逻辑，部分供应商会因此直接报 400。要用这个会话前建议先确认，或另开新会话。

### 3.2 取证质量上的残留（不是运行期对象）

- `LogOutput.log` 尾部落盘不完整：文件里最后是 4 条 `[输入]`，`call_5` 的两行丢了；且配置 `LogLevels = Fatal, Error, Warning, Message, Info` 本身不含 Debug。

- `DSPGAME.gc.log` 只有一行 `SuspendThread loop failed`（崩溃处理器挂起线程失败，Wine 下常见）。

### 3.3 没有残留的部分（已确认）

- 脚本沙箱是纯内存的：QuickJS-WASM 在 sidecar 进程内，脚本结束/进程存活都不落任何临时文件。
- 该脚本是只读的：只出现 `game_get_planets` / `game_get_planet`，没有写工具字面量，没有脚本租约（`ConfirmationService.ScriptLease` 只在写脚本时签发），没有蓝图、没有建筑、没有存档写入。

## 四、为何会出现这种情况

### 4.1 已经能证实的

1. **触发路径是脚本，但不是「脚本执行到一半崩了」**：脚本 #2 的第一次调用没有进入分发器，游戏是在两次调用之间的空档死的。
2. **崩溃是原生崩溃**：`Player.log` 里没有托管异常、没有 `Stack overflow`、没有 `Out of memory` 文本；栈顶几帧全在 `mono-2.0-bdwgc.dll` 的 `.text`（RVA ≈ 0x4E2F8F、0x4E3246、0x4F7E1B、0x4F819B、0x4F86DF），下面是 `UnityPlayer.dll`、`DSPGAME.exe`、`kernel32`、`ntdll`。
3. **崩溃处理器自身不健康**：`SuspendThread loop failed` 说明挂起线程失败，转储里只有十几帧，没法当调用栈用。
4. **这不是已知的老问题**：`Player.log` 里 `Crash!!!` 只出现 1 次，`Player-prev.log` 为 0 次，属于首例。
5. **现场代码版本**：已安装 `IcarusII.dll` 与 `dist/thunderstore` 的 1.1.247 一致（对应提交 `22fc162`）；当前 HEAD 只多了依赖升级与打包检查（`8c1c18a` / `8c40e9c` / `2311a76`），崩溃相关代码在两者之间没有差异。

### 4.2 目前不能证实、但必须记下来的

- 栈顶落在 mono GC/分配路径上，形状上像「托管代码正在分配或 GC 时被打断」，这类现象通常来自堆损坏、越界写、或某次原生调用传了坏指针；本次工作负载很小（248 颗行星的只读汇总），不像单纯的内存耗尽。
- 空档期游戏侧唯一在动的是聊天窗流式渲染（思考块 + 正文 + `run_script` 工具块），但 UI 路径没有任何日志和异常记录，无法据此指认。
- 也无法证明「与脚本完全无关」，因为崩溃那一刻 mod 侧没有任何日志。

### 4.3 这次脚本本身值得注意的设计事实（不是结论，是风险面）

- `dsp.call` 走同一个 `GameToolHost`，每一次调用都是一次完整的主线程工具任务，脚本通道把单次超时压到 8000ms（`tools/script.ts`：`Math.min(8000, deadline - Date.now())`）。
- 脚本重放机制是「抛出挂起 → 宿主执行 → 从头重放并命中 memo」，10 次调用意味着脚本被完整重跑 10 遍（本次数据量小，代价可忽略）。
- 这类「模型自己决定循环多少次」的批量读取，玩家在界面上只看到一个「脚本」块，中间没有逐次反馈；一旦某次调用卡住，玩家的体感就是游戏卡死。
- `PlanetJob` 对「远程未加载行星」只有 `factory == null` / `runtimeVeinPool` 空判这两道防线，正常玩法里这颗行星永远是本星，远程路径平时几乎不被走到。

### 4.4 还缺的证据（要定位到行，必须补）

1. Unity 崩溃转储：`Temp/.../Crashes` 为空，需要下次开启崩溃上报或让 Proton 生成 core。
2. `mono-2.0-bdwgc.dll` / `UnityPlayer.dll` 的符号：目前只能算到 RVA，符号表没有，栈顶函数名未知。
3. mod 侧「崩溃瞬间在做什么」：`LogOutput.log` 的末尾丢了 `call_5` 之后的内容，只能靠 `Player.log` 反推「之后什么都没做」。
4. 玩家的体感细节：是「先卡住十几秒再崩」还是「瞬间消失」，这决定要不要往死锁/挂起方向查。

## 六、复现结果（21:52–22:08，全部未复现）

测试用沙盒档可以随便赌，所以按「先还原调用，再压 GC」的顺序做了四轮：

| 轮次 | 手段 | 覆盖内容 | 结果 |
| --- | --- | --- | --- |
| 1 | `!tool game_get_planets {"includeVeins":true}` | 现场 `call_5` 的同一发调用（调试通道，20000ms） | 成功，`elapsed=3ms`，248 行星，无异常 |
| 2 | 同一句原话再问一遍，让模型自己写脚本 | 5 段 `run_script`：3×`game_get_planets`、1×13 行星循环、1×`kb_search` 循环；mod 侧 19 次调用 19 次完成、0 错误，其中 15 次走脚本通道（8000ms） | 无异常 |
| 3 | 逐字重放现场脚本 #1 / #2 | 与现场完全一致的代码（含 `maxCalls`） | 无异常 |
| 4 | 压 GC：同一发调用连续 300 次、每次换 `seed` 绕开结果缓存 | `calls: 300`、`elapsedMs: 114080`、`rounds: 300`，约 114 秒连续分配与 WS 往返 | 无异常 |

结论：
- **「这个工具 / 这段脚本把游戏搞崩」不成立**：同样的调用单发、批量、连续 300 次都没有任何异常。
- 崩溃点落在「工具结果返回后 0.9 秒」更像是引擎侧事件的巧合，栈顶在 `mono-2.0-bdwgc`（GC）与崩溃处理器挂不起线程，形态偏向引擎/mono 层的 GC 中止；其他 Unity 游戏也有同类「Fatal error in GC」报告（如 Cities: Skylines II）。
- 现有证据仍不足以把责任判给 mod 或判给引擎，只能说**未能在工具路径上复现**。
