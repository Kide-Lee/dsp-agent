# 多会话并行可行性评估

> 评估时间：2026-11-04。
> 范围：同一存档内玩家同时进行多个会话（多个 pi 会话并行回答/执行工具），不包含多人联机。
> 方式：静态阅读协议、sidecar、mod 与游戏工具层实现；评估后按 `pi-parallel-sessions` 落地了并行会话，见第 9 节。

## 0. 结论

**技术上可行，但不建议直接做“所有会话都能并行读写”。**

当前实现是严格的单飞模型（同一时刻只有一个 pi 会话、一轮回答、一个可见正文、一个确认页）：

- 同一存档已经有多个会话的**存储与索引**（A.13），但活动会话只有一个。
- 切会话、新建、删除在回答期间都会返回 `busy`，必须先等当前回答结束。
- `PiAgent` 只有一个 `session`、一个 `active` 运行状态，且所有 prompt 走一条全局串行链。
- mod 只有一个聊天正文、一个 `_streaming`、一个确认面板、一个提问面板。

建议分三层推进：

1. **先修多会话的正确性**：turn 级操作（删除回合、撤销压缩）和卡片/时间记录必须带 `conversationId`，
   否则现在“一个存档多个会话”在删除/回放时已经可能串到别的会话。
2. **再做“多会话并存 + 单执行槽”**：可以随时切会话，长任务在后台继续跑，另一会话的提问排队；
   同一时刻仍然只有一轮回答。绝大多数“别让我干等”的需求在这一层就能满足，风险最低。
3. **本轮已按第 3 层实现**：每个会话独立 `AgentSession`，不同会话可同时跑；
   mod 只显示焦点会话，切到后台不打断运行。写操作按建筑/工厂/星球层级加锁，
   后台会话遇到需要玩家确认/提问/动 UI 的操作会等切到前台；`takeover` 或 `limited` 的
   risk 1 仍可在后台自动放行。实现细节与已知限制见第 9 节。

多游戏实例（同时开两个游戏各连一个 sidecar）不属于本功能，且按当前配置不可行：默认固定端口 `8765`、
共享数据目录与 `runtime.json`、共享 BepInEx 配置；两个实例会抢端口和运行时文件。

## 1. 先明确“同时”的三种含义

| 含义 | 玩家看到的行为 | 当前支持 | 评估 |
| --- | --- | --- | --- |
| 多会话并存、顺序执行 | 多个会话各有历史；可随时切换；提问按队列逐个回答 | 部分支持，但切换被 `busy` 阻断 | 推荐先做，成本最低 |
| 多会话并行执行 | 两个会话同时调模型/工具，各自流式输出 | 不支持 | 可行，但需重构，建议限制为“前台可写 + 后台只读” |
| 多游戏实例/多人 | 两个游戏进程各有一个 Agent | 不支持 | 不在本功能范围，也不建议 |

后文默认讨论前两种。

## 2. 当前实现边界

### 2.1 协议层

- `prompt.conversationId` 已经存在，但它必须等于 sidecar 的**全局活动会话**，否则返回
  `conversation_mismatch`，见 [session.ts:1526](../../sidecar/src/session.ts#L1526) 与
  [session.ts:1547](../../sidecar/src/session.ts#L1547)。
- `conversation.create` / `conversation.switch` / `conversation.delete` 在任意一轮回答运行期间都返回
  `busy`，见 [agent.ts:2083](../../sidecar/src/agent.ts#L2083)、
  [agent.ts:2114](../../sidecar/src/agent.ts#L2114)、
  [agent.ts:2229](../../sidecar/src/agent.ts#L2229)。
- 运行期帧没有统一的 `conversationId`；`stream` / `message` / `error` 只有 `replyTo`（prompt id），
  而 `status`、`tool_activity`、`tool_call`、`confirm_request`、卡片、`context.compacted` 连 prompt id 都没有：
  - `status` 没有会话标识，见 [protocol.ts:1832](../../sidecar/src/protocol.ts#L1832)；
  - `stream` 只有 `channel` + `delta`，见 [protocol.ts:1922](../../sidecar/src/protocol.ts#L1922)；
  - `tool_activity`、`tool_call`、`confirm_request`、`blueprint_card`、`link_card`、
    `context.compacted` 连 prompt id 都没有；`error` 有 `replyTo`，但没有会话标识。
- `abort` 没有目标会话，只能中断“当前”这一轮，见 [session.ts:1613](../../sidecar/src/session.ts#L1613)。
- `history.delete` / `history.undo_compaction` 没有 `conversationId`；sidecar 按“目录里最新修改的
  session 文件”定位，见 [agent.ts:2564](../../sidecar/src/agent.ts#L2564) 与
  [agent.ts:2639](../../sidecar/src/agent.ts#L2639)。

协议设计稿里其实已经出现过 `stream {conversationId, ...}` 的设想（见 [design.md:372](../design.md#L372)），
但实现没有落地。

### 2.2 sidecar 层

核心单例状态都在 `PiAgent`：

- `private session: AgentSession | null`，见 [agent.ts:1324](../../sidecar/src/agent.ts#L1324)；
- `private active: RunState | null`，见 [agent.ts:1327](../../sidecar/src/agent.ts#L1327)；
- `private chain` 全局串行链，见 [agent.ts:1349](../../sidecar/src/agent.ts#L1349)；
- `run()` 把所有连接的所有 prompt 串到同一条链上，见 [agent.ts:2736](../../sidecar/src/agent.ts#L2736)；
- `handleEvent` 只认 `this.active`，见 [agent.ts:3874](../../sidecar/src/agent.ts#L3874)；
- `abort()` / `steer()` 只作用于 `this.session` 和 `this.active`，见
  [agent.ts:2763](../../sidecar/src/agent.ts#L2763) 与 [agent.ts:2780](../../sidecar/src/agent.ts#L2780)；
- `ensureSession` 按全局活动会话加载唯一的 pi 会话，见 [agent.ts:3749](../../sidecar/src/agent.ts#L3749)；
- `switchConversation` 在改完活动会话后直接 `teardown()`，因此“切走再切回”会丢掉内存里的运行态，
  见 [agent.ts:2149](../../sidecar/src/agent.ts#L2149)。
- pi 自带的 `AgentSessionRuntime` / 扩展 API 用 `newSession` / `switchSession` **替换**当前会话：
  `switchSession` / `newSession` 会先走 `teardownCurrent()`，对旧会话 `await session.abort()` 再
  `session.dispose()`，然后才 `apply()` 新会话。也就是说“替换”会终止旧会话，不能当作并行开关；
  真正的并发会话需要我们自己持有多个独立 `AgentSession`（各自的订阅、abort、run 状态），
  不能指望单个 `AgentSessionRuntime` 同时跑多个。

工具宿主同样只有一个 transport：

- `GameToolHost` 的 `private transport` 只有一个，见 [host.ts:78](../../sidecar/src/tools/host.ts#L78)；
- 每轮 prompt 前 `bind(emit)`、结束后 `unbind(emit)`，见 [host.ts:199](../../sidecar/src/tools/host.ts#L199)。

同一连接下两个 run 的 `emit.callTool` 恰好都指向同一个 `Session`，所以“工具还能跑”并不说明并发安全；
一旦多连接，或者出现 bind/unbind 交错，工具调用就会串到别的连接。`active` 的覆盖比 transport 更致命：
第二个 run 会覆盖第一个 run 的 `active`，第一个 run 的流式事件、工具状态、收尾都会走错。

此外 `onConfigChanged` / `onClientCapabilities` / `onSaveChanged` / `onSandboxChanged` 都用单个
`this.active` 判断“当前能不能拆会话”；并行后必须等所有 run 结束。

### 2.2.1 上游先例：pi-parallel-sessions 与 pi-sessions

- [`pi-parallel-sessions`](https://www.npmjs.com/package/pi-parallel-sessions)（liushihao456，npm 0.2.8）
  已经实现了“一个进程内多个 live session”：每个子会话是一个独立的
  `AgentSessionRuntime + InteractiveMode`，切换只 `stop()` 非活动会话的 TUI，agent runtime
  仍在后台跑；另有一套共享 path lock，写文件前检查冲突。
- 它证明 SDK 层面可以在一个 Node 进程里同时跑多个 `AgentSession`，不需要用
  `switchSession` 替换；但它只解决 TUI 与文件路径冲突，不解决游戏世界、确认、提问、
  撤销、待办、工具 transport 的隔离。
- [`pi-sessions`](https://www.npmjs.com/package/pi-sessions)（thurstonsand，npm 0.22.1）是另一个插件：
  会话搜索 / ask / handoff / 自动标题 / 索引 / subagent，不是进程内多会话复用器；
  它的并行部分主要靠外部 pane/process（tmux/Ghostty/Herdr）与消息 broker。
- 注意命名冲突：npm 的 `pi-parallel-sessions` 仓库名也叫 `pi-sessions`，但它不是
  npm 的 `pi-sessions` 包。评估并行实现时应以 `pi-parallel-sessions` 为参考。

### 2.4 游戏侧

- 玩家只有一个世界、一个主线程；工具执行由 `GameToolDispatcher` 分帧推进，
  同时最多 4 个活动调用，见 [GameToolDispatcher.cs:66](../../mod/src/IcarusII/Game/Tools/GameToolDispatcher.cs#L66) 与

### 2.5 持久化层

- 每个会话一个 pi session 文件，放在 `<data>/sessions/<saveKey>/`，这一点对并行是友好的。
- `active.json` 只记录一个活动会话，见 [agent.ts:1492](../../sidecar/src/agent.ts#L1492)；
  “焦点”和“正在运行”目前是同一个概念。
- 蓝图卡片、链接卡片、回答游戏时间按**存档**记录，并按用户提问原文匹配回合：
  - [blueprint/card.ts:197](../../sidecar/src/blueprint/card.ts#L197)
  - [link/card.ts:112](../../sidecar/src/link/card.ts#L112)
  - [history/game-time.ts:20](../../sidecar/src/history/game-time.ts#L20)

  同一存档里两个会话出现相同提问文本时，历史回放可能把卡片/时间挂到另一个会话的回合上。
- `history.delete` / `undoCompaction` 按“最新文件”定位，切换到一个旧会话后删除回合，
  可能改到另一个刚用过的会话文件；见 2.1 的引用。

## 3. 直接开并行会遇到什么

| 约束 | 直接开并行后的现象 | 必须的改造 |
| --- | --- | --- |
| `PiAgent.active` 单槽 | 第二个 run 覆盖第一个；流式、工具状态、终止都走错 | 每会话一个 `RunState`，事件订阅按 run 捕获 |
| `PiAgent.chain` 全局串行 | 就算加槽也仍然排队，没有真正并行 | 改成每会话队列，另设全局并发上限 |
| 单个 `session` | 只能加载一个上下文；切会话要 teardown | 会话池（LRU/固定上限），按 conversationId 取 |
| 单 transport | 工具调用归属取决于最后一次 bind，多连接会串线 | 按连接/run 绑定，或每 run 独立 transport |
| 帧无 `conversationId` | A 的正文/思考/工具卡会画进 B；A 的 `idle` 会把 B 的“回答中”清掉 | 所有运行期帧带可选 `conversationId`，mod 路由 |
| 单正文/单 `_streaming` | 切换清屏，后台流破坏当前会话 | 每会话 UI 状态，或 sidecar 缓冲 + 焦点重放 |
| 单确认页 | 后台写请求被 `busy` 拒绝，或弹到前台会话里 | 确认队列 + 来源会话；后台默认不允许写 |
| 单 `ask_user` | 后台提问抢前台面板，或直接 `busy` | 只允许前台会话提问；后台返回明确错误 |
| 单撤销栈/待办组/tether | 两个 Agent 互相覆盖，玩家无法判断撤销/待办归属 | 写操作串行 + 前台独占；或每会话独立 |
| Node 单线程 + 同步 CPU | `run_script`、蓝图规划会阻塞所有会话的网络与流式 | 重 CPU 任务串行，或移入 worker |
| 端口/数据目录固定 | 第二个游戏实例启动 sidecar 抢 8765、共享 runtime.json/config | 不支持多实例；不要作为本功能目标 |

## 4. 可行方案

### 方案 A：多会话并存 + 单执行槽（推荐先做）

**目标**：玩家可以同时保留多个会话，随时切换；长任务在后台继续；同一时刻仍然只跑一轮回答。
这不是“并行回答”，而是“多会话并存 + 后台继续 + 提问排队”。

核心改造：

1. **把“焦点会话”和“运行会话”拆开**
   - `active.json` 只表示焦点；
   - `prompt` 带上目标 `conversationId`，sidecar 按该 id 打开/复用会话，不再要求它等于焦点；
   - 运行中的会话与焦点解耦，切走不 teardown。

2. **切会话不再 `busy`**
   - `conversation.switch` 只改焦点、返回目标历史，不打断正在跑的会话；
   - `conversation.create` 在运行中也可用（新空会话作为焦点）；
   - `conversation.delete` 只拒绝“正在运行的那个会话”，其他会话可删。

3. **每会话一个 prompt 队列**
   - 同一会话的提问串行；不同会话的提问进入各自队列；
   - 只有一个执行槽，队首按策略调度（建议前台优先，或严格 FIFO）。

4. **后台运行不污染前台 UI**
   - 所有运行期帧带 `conversationId`；
   - mod 只渲染焦点会话；后台会话的流式帧可丢弃，或由 sidecar 缓冲；
   - 后台会话完成时发 `conversation.activity`（running/idle/unread/error），左侧索引显示转圈/未读；
   - 切回正在跑的会话时，显示“正在回答”；如果 sidecar 有快照，则重放当前进度。

5. **前台独占的操作**
   - 写操作、`ask_user`、确认页、`open_panel`、相机、标记、`ui_click` 只允许焦点会话；
   - 后台会话调用这些工具时返回明确的 `not_foreground`（新增错误码）或排队等焦点；
   - 读工具、知识库、wiki、本地计算在后台可用。

**改动量**：中等。协议加可选字段和少量语义；sidecar 需要把 prompt 路由从“全局活动会话”改成“按 id”，
但仍是单 run，不需要会话池与事件多路复用；mod 需要焦点/运行状态区分和索引指示，
但不一定需要把整个聊天正文重构成多实例。

**主要风险**：如果后台会话继续跑，而玩家切走，写操作在前台独占策略下会被拒绝，模型需要学会请玩家切回；
这是产品交互问题，不是不可克服的技术问题。

### 方案 B：前台可写 + 后台只读的两路并行（推荐上限）

**目标**：真正同时跑两个会话：例如一个长蓝图规划在后台，另一个快速问答在前台。

从 pi SDK 的类型定义看，`createAgentSession` 每次返回独立的 `AgentSession`，当前代码没有依赖进程级单例；
真正的阻碍在本项目的 `PiAgent` 封装（单 `session` / 单 `active` / 全局 `chain`），不在 SDK 本身。
不过多会话共享同一个 `ModelRuntime`、并发压缩/重试、事件订阅归属仍需要实测验证。

核心改造：

1. **会话池与 run 池**
   - `Map<conversationId, AgentSession>`，最多 2 个活跃；空闲会话可 LRU 卸载，需要时从文件重建；
   - `Map<conversationId, RunState>`，每个 run 有自己的 `emit`、`AbortController`、工具集、错误状态；
   - `session.subscribe` 的闭包捕获该 run，不再读全局 `this.active`；
   - 删除全局 `chain`，改为每会话串行 + 全局并发上限 2。

2. **帧路由**
   - `stream` / `message` / `status` / `tool_activity` / `tool_call` / `confirm_request` /
     `blueprint_card` / `link_card` / `context.compacted` / `error` 增加可选 `conversationId`；
   - `abort` 增加可选 `conversationId`；
   - mod 按 id 路由到对应会话的 UI 状态或后台缓冲。

3. **写操作与前台独占**
   - 后台会话的工具白名单只含读/规划/知识库；写工具、确认、`ask_user`、UI 操作直接拒绝；
   - 前台会话持有“写租约”，同一时刻最多一个写 run；
   - 权限档位必须能按会话生效，至少后台强制只读；不能因为全局是“接管”就让后台会话自动写，
     否则玩家看不到的操作会在后台静默执行；
   - 单层撤销栈、单待办组、tether、标记仍由前台独占，避免归属混乱。

4. **UI**
   - 两种实现路径：
     - **低 UI 风险**：sidecar 为每个 run 维护事件日志/快照；mod 仍只有一个正文，切会话时清屏并重放目标会话的进度，之后继续收流；
     - **高 UI 自由度**：mod 每会话一个 ChatView（可隐藏），各自维护流式/工具块/卡片；切换只换可见根节点。
   - 左侧索引增加运行中/未读/错误指示；确认页标注来源会话；窗口关闭时后台完成用一条汇总通知，不逐条刷。

5. **CPU 与工具争用**
   - `run_script`、蓝图规划等同步重活全局只允许一个；
   - 游戏工具同时最多 2 个（现在 dispatcher 允许 4，但主线程预算有限）；
   - 读缓存继续按存档共享，避免两个会话重复扫描工厂。

**改动量**：大。sidecar 的 PiAgent 需要从“单会话单 run”改成“会话池 + run 池”，这是本次评估中最大的一块；
mod 若选低 UI 风险路径，正文层改动可控，但协议/索引/确认/提问/终止都要改。

**主要风险**：
- 模型并发请求触发供应商限流（429），需要全局并发上限和退避；
- 两个会话读同一世界，结果会随对方/玩家的操作变化，模型可能基于过期快照回答；
- 主线程工具争用导致帧率下降；
- 确认/提问的来源和优先级需要产品规则，否则玩家会被后台弹窗打断。

### 方案 C：全并行读写（不建议）

如果允许两个会话同时写游戏世界，还需要：

- 每会话独立撤销栈（现在只有一层全局 `_last`）；
- 每会话独立待办组（原生目标面板的固定组不够）；
- tether/标记/相机/面板的归属与互斥；
- 写冲突检测或区域锁（两个 Agent 同时改同一片工厂）；
- 每会话权限档位（现在权限是全局配置，确认页自动同意也按全局/插件策略）；
- 确认队列与来源标注，`ask_user` 队列；
- 每个会话独立的蓝图工作目录（现在 `BlueprintWorkspace.cwd` 是单例）；
- 卡片/时间记录按会话隔离。

这些不是“加个并发开关”能解决的，而是游戏世界语义和产品交互问题。除非明确要做“多个 Agent 同时改造工厂”，
否则收益远小于风险。

### 方案 D：多游戏实例（不建议）

当前 `SidecarPort` 默认 8765（[PluginConfig.cs:185](../../mod/src/IcarusII/Config/PluginConfig.cs#L185)），
数据目录默认共享 `%APPDATA%/icarus-ii`，`runtime.json` 与 `config.json` 也共享。
两个游戏实例会抢端口、覆盖运行时文件、共享会话目录。要支持只能给每个实例独立端口和数据目录，
但 BepInEx 配置本身也是共享的；这不是玩家级功能，不建议投入。

## 5. 无论选哪个方案，都建议先修的正确性问题

> 2026-11-04 补充：下面的 1–5 已实现并补了离线测试；并行实现的边界见第 9 节。

这些问题在“单执行槽 + 多会话”下就已经存在，不是并行才出现：

1. **`history.delete` 按最新文件定位**
   - 现在没有 `conversationId`，切到旧会话后删除回合可能改到另一个文件；
   - 建议：协议 A.7 增加可选 `conversationId`；sidecar 按 id 解析 session 文件；老 mod 不传时保持原行为。
2. **`history.undo_compaction` 同样按最新文件定位**
   - 建议同上，协议 A.11 增加可选 `conversationId`。
3. **卡片/时间记录按提问原文匹配**
   - 同一存档两个会话出现相同提问文本时，回放会串；
   - 建议：新记录写入 `conversationId`，回放优先按 id，老记录退回原文匹配。
4. **`active.json` 的“焦点”语义**
   - 明确它是 UI 焦点，不是“唯一可运行的会话”；运行态另存。
5. **删除/重命名运行中的会话**
   - 明确返回 `conversation_busy`，不要删掉正在写的 session 文件。

## 6. 验证矩阵（若进入实现）

### 6.1 离线

- 协议：新增可选字段的序列化/反序列化，老端忽略未知字段；`conversationId` 缺失时退回单会话行为。
- 协议：`abort` 带/不带目标；`history.delete` 带/不带 `conversationId`。
- sidecar：两个会话的 prompt 队列互不阻塞；A 的 `abort` 不影响 B；A 的 `idle` 不清 B 的 busy。
- sidecar：后台写工具被 `not_foreground` 拒绝；前台写仍走确认 + 令牌。
- sidecar：改配置/换存档/能力变化时等待所有 run 结束再 teardown。
- 持久化：同一提问文本出现在 A/B 两会话，卡片/时间各自挂回；删除 B 的回合不动 A 的文件。
- mod：新增帧类型/字段的解析与未知字段忽略；会话索引运行/未读状态。

### 6.2 实机（真实 LLM，不用 mock）

1. 在 A 发长任务（蓝图规划/大范围分析），立即切到 B 问一个短问题；B 的回答不受 A 影响；切回 A 能看到进度或完成结果。
2. A 在后台尝试写操作/`ask_user`：得到明确提示，不弹到 B 的界面；B 的前台写操作正常确认、撤销只撤销 B。
3. 在 A 运行中删除 B 的回合：只改 B；A 的上下文不受影响。
4. A、B 使用同一句提问分别生成蓝图卡：历史回放各自挂对。
5. 两路并行时持续移动/建造，观察帧率、工具超时、流式卡顿；供应商限流时一路失败不拖垮另一路。
6. 换存档/退出游戏：所有 run 终止，重进后历史与卡片正确。

## 7. 建议

- **如果目标只是“玩家不用等当前回答结束才能看别的会话”**：做方案 A。成本远低于真并行，已经能消除当前最明显的阻塞。
- **如果目标包含“长任务后台跑，同时前台还能得到新回答”**：在方案 A 稳定后做方案 B，但把并发上限设为 2，
  且后台只读。不要一上来就做全并行写。
- **不建议**把“多游戏实例”当作多会话方案；也不建议在没有会话级归属的情况下开放后台写操作。
- 实施顺序建议：
  1. 修 5 中的正确性问题（尤其 `history.delete` / `undoCompaction` / 卡片归属）；
  2. 做焦点/运行分离与切会话不打断（方案 A）；
  3. 观察真实使用中“排队等待”是否仍是瓶颈；
  4. 再决定是否投入方案 B。

## 9. 已落地的并行实现（按 pi-parallel-sessions 思路）

### 9.1 运行模型

- sidecar 的 `PiAgent` 从“一个 `session` + 一个 `active`”改为 `Map<conversationId, ConversationSlot>`。
  每个 slot 持有独立的 `AgentSession`、`ModelRuntime`、事件订阅和当前 `RunState`。
- 同一会话的 prompt 走该会话自己的队列，串行执行；不同会话直接并行。
  进程级最多同时跑 3 个会话，避免一次创建过多模型请求。
- `conversation.switch` / `conversation.create` 只改焦点，不再 `teardown`，也不再返回 `busy`。
  切换不会中断任何会话；`abort` 带可选 `conversationId`，缺省作用于焦点会话。
- 删除正在回答的会话返回 `conversation_busy`；删除空闲会话只释放它自己的 slot。

### 9.2 焦点与显示

- 运行期帧（`status` / `stream` / `message` / `tool_activity` / 卡片 / `context.compacted` /
  `error`）带可选 `conversationId`；sidecar 只向焦点会话发这些帧。
- `conversation.switched` / `conversation.created` 带 `running` 与 `state`，mod 用它恢复
  发送/中断按钮，不依赖全局状态。
- 切回一个仍在回答的会话时，sidecar 在回执后补发一条 `stream`，内容为 `RunState.text`
  已生成的部分；之后的新增量继续流式发送。切走期间的工具卡/思考块不重放，终稿仍完整。
- mod 对运行期帧再做一次焦点过滤；后台 `tool_call` 仍执行，但不画卡片、不改进度状态。
- 焦点会话切换时 mod 清空旧正文、重放目标历史，并按目标 `running` 调 `SetBusy`；
  因此按钮只反映焦点会话，后台完成不会把前台的「中断」清成「发送」。

### 9.3 资源锁

- 锁 key：
  - `building:<id>`：一台建筑（文件）；
  - `planet:<id>:factory:<id>`：传送带/分拣器连起来的建筑群（目录，预留）；
  - `planet:<id>`：一颗星球的全部工厂（仓库）；
  - `global`：研究、面板、待办、撤销、第三方配置等玩家级操作。
- 冲突按路径前缀判断；`planet` 锁保守地覆盖所有 `building`/`factory` 锁，
  因为部分建筑工具没有 `planetId`，无法安全判断跨星球同 id。
- 写工具锁映射：改配方/批量/存储/投料/取成品按建筑；`game_copy_blueprint` 读取整片建筑，
  按星球锁保证蓝图快照一致；面板/研究/待办/标记/传送/第三方配置按全局；
  `run_script` 本身不占锁，脚本内的写调用各自加锁。
- 工具执行前加锁，`tool_result` / 超时 / 取消 / 断线都会释放。同会话重入，
  不同会话等 3 秒仍冲突则返回 `resource_locked`。
- 工厂层级目前只预留 key：现有工具没有稳定的 `factoryId`，还没有从传送带连通分量
  推导工厂 id 的游戏侧实现；因此当前实际使用的是建筑/星球/全局三层。

### 9.4 后台交互门控

- 需要玩家确认的写操作：后台会话先等切到前台；`limited` 的 risk 1 与 `takeover` 的写操作
  由 mod 按权限自动放行，后台可直接执行。
- `ask_user`、`game_open_panel`、`ui_click` 始终等前台，避免后台会话抢面板/弹提问。
- 脚本级确认也等前台；脚本结束立即释放租约。
- 后台写操作仍可能改变世界/待办等全局状态，锁只能防止同一资源的并发写，
  不能消除业务冲突；这是并行模式的固有限制。

### 9.5 已知限制

- 后台会话完成时 `reply.time` 被抑制，历史里该回答的游戏时间可能显示 `--:--`。
- 切回运行中会话只补正文，不重放切走期间的思考块和工具卡；终稿和历史不受影响。
- 撤销栈仍是全局单栈；两个会话并发写不同建筑时，撤销顺序按实际写入顺序，
  不按会话隔离。
- 工厂锁没有自动推导；要真正按工厂并行，需要 mod 侧提供传送带/分拣器连通分量，
  或由工具显式传 `factoryId`。
- 当前仍是单聊天窗：同一时刻只显示一个焦点会话，不做分屏/多窗口。
