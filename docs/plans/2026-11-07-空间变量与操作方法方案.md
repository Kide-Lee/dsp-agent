# 空间变量与操作方法方案

> 输入：[dsp-agent.xlsx](../dsp-agent.xlsx)。区域页 10 类；定点页 8 类（6 类实体 + 2 类坐标，其中垃圾块是自由动点，建议移到动点页）；动点页 10 类。
> 目标：为 Agent 定义一套可构造、可求值、可查询、可行动、可回放的空间变量与方法层。
> 结论：不要直接做 `Region` / `FixedPoint` / `MovingPoint` 三个孤立结构体。先把「锚 + 形状 + 运动 + 时刻」统一成 `SpatialValue`，再按能力分派方法。

## 0. 一页结论

1. **三类变量统一为一个 `SpatialValue`**：`kind`（region/point/motion）+ `type`（具体种类）+ `epoch`（运行期身份）。区域页的 10 类、定点页的 8 类、动点页的 10 类都是它的不同 `type`，不是 28 个孤立结构体。
2. **区域必须拆成两种能力**：`Area`（几何包含、距离、边界）与 `Collection`（成员枚举、统计、层级）。电网、工厂只有 `Collection`；行星区域、世界区域两者都有；恒星系、行星是层级容器。
3. **定点/动点是坐标系相对的，不是“会不会动”的字面区分**。建筑在行星表面固定，但在宇宙系里随自转/公转移动；宇宙点在银河系固定，但行星会穿过它。表格里的「定点」按对象类别分，不是按绝对静止分：太空黑雾建筑随巢穴轨道运动，垃圾块会漂移/坠落，世界坐标在银河系固定，行星坐标在行星系固定。用 `anchor` + `motion` + `frame` + `t` 描述。
4. **方法分四层**：构造 → 求值/转换 → 关系/度量 → 行动。前三层是纯查询；第四层复用现有工具，不另起一套。
5. **对模型只加 3 个只读查询工具**：`space_region` / `space_point` / `space_motion`；变量命名另加 1 个可选的 `space_var`（P1）。行动仍走 `game_analyze_area`、`game_capture_view`、`game_tether_add`、`game_copy_blueprint` 等现有工具，通过新增 `region` / `point` 参数接入。
6. **P0 先做能精确落地的部分**：建筑/矿脉/植被/垃圾块快照/表面坐标/世界坐标，恒星系/恒星/行星/行星区域/世界长方体/球体，以及 `contains` / `distance` / `members` / `stats`。电网、工厂、动点、黑雾、戴森球分阶段。
7. **所有空间结果带 `gameTick`、`epoch`、`partial`、`truncated`**。运行期 ID 失效必须显式报 `stale`，不能静默回退到别的建筑或别的行星。

## 1. 为什么不能按十种区域写十个 `contains`

### 1.1 十种区域不是同一类东西

| 类型 | 判定依据 | Area | Collection | 层级 |
| --- | --- | --- | --- | --- |
| 恒星系 | 以恒星为中心、`StarData.systemRadius` 为半径的范围 | ✓ | ✓ 行星 | ✓ 恒星/行星/黑雾巢穴/戴森球 |
| 恒星 | 恒星本体，`StarData.radius` / `physicsRadius` | ✓ | — | — |
| 行星 | 行星本体 + 大气层，`realRadius + atmosphereHeight` | ✓ | ✓ 建筑/矿脉/玩家/黑雾基地 | ✓ 电网/工厂 |
| 电网 | 同一 `PowerNetwork` 的建筑，以及被该电网节点覆盖的建筑 | — | ✓ 建筑 | — |
| 工厂 | 同一电网内、由传送带/分拣器连通的建筑群 | — | ✓ 建筑 | — |
| 太空黑雾巢穴 | 巢穴本体、建筑、单位；`hiveAstroId` + 轨道 | △ | ✓ 建筑/单位 | — |
| 地面黑雾基地 | 基地本体、建筑、单位；`DFGBaseComponent` + `BASE_RADIUS` | △ | ✓ 建筑/单位 | — |
| 戴森球 | 戴森云 + 戴森壳；按层或整球 | ✓ 壳 | ✓ 层/节点/太阳帆 | ✓ 层 |
| 世界区域 | 银河坐标系下的轴对齐长方体 | ✓ | ✓ 范围内已加载实体 | — |
| 行星区域 | 行星经纬度矩形，径向投影 | ✓ | ✓ 范围内已加载实体 | — |

`△` 表示只能给包围体/近似范围，不是精确边界。

**规则**：某个方法需要的能力不存在时，返回 `unsupported_capability` 并给出替代方法；不要给一个看似合理的几何答案。例如「这个点在不在这座工厂里」不能用一个外接矩形来回答，应该返回「工厂没有 Area 能力，请用 `members` 或 `nearestMember`」。

### 1.2 定点/动点是坐标系相对的

同一个位置，在不同参考系里「动」与「不动」是相反的：

- 建筑：固定在行星表面；在行星系里不动，在宇宙系里随行星自转/公转移动。
- 宇宙坐标点：在银河系里不动；行星会周期性穿过它。
- 行星中心：在宇宙系里公转，是动点；在「以行星为中心」的局部系里不动。
- 物流船：在行星系和宇宙系里都在动。
- 垃圾块：表里放在定点，但 `TrashData` 有速度、寿命、落点，实际会漂移/坠落；`point.trash` 只能是当前快照，跟踪要用 `motion.trash`。

你补充的表也是按对象身份分的：定点页 6 类实体 + 2 类坐标，动点页 10 类移动对象。这个分法适合做目录（id 来源、数据源不同），但不能直接当成运动学分类；运动学分类要看 `frame` 和 `t`。

所以不能把「定点」「动点」写成两个互斥的类型。建议：

- `anchor`：身份锚。`surface` / `universe` / `entity` / `celestial`；`entity` 再分 `building` / `vein` / `vegetation` / `df_space_building` / `df_ground_building` / `trash`。
- `motion`：在这个锚上的运动模型。`static` / `tracked` / `analytic`。
- `frame`：这次求值用哪个坐标系。`universe` / `planet` / `surface`。
- `t`：求值时刻，用 `gameTick`（60 tick/秒），默认当前 tick。

**定点** 在本文指表格里的对象类别；求值上是 `motion=static` 的 `Point`（如果锚本身在动，比如太空黑雾建筑/垃圾块，仍按 `t` 重算）。**动点** = `Motion`。
一个表面定点在 `frame=universe` 下求值时会随时间移动；一个宇宙定点在 `frame=planet` 下求值时会随行星移动。这是物理事实，不是类型错误。

### 1.3 现有工具的缺口

这套变量不是凭空加的，它要解决现有工具的四个具体问题：

1. `game_analyze_area` 的范围是行星局部 XZ 平面上的球形切分，靠近极点时与游戏网格有偏差；它也没有「经纬度矩形」这种玩家真正会说的范围。
2. `game_get_entities` 只能按整颗行星、原型、配方过滤；模型要自己算「哪些建筑在这片区域里」，既费 token 又容易算错。
3. 位置输出已经是「星系 + 行星 + 经纬度」，但输入侧仍各自要求 `center` + `radius`：截图、tether、布局图、蓝图各有一套，无法复用同一个区域。
4. 电网、工厂、黑雾基地、戴森球这些「不是几何体」的区域，现有工具完全没有统一抽象；模型只能靠 `game_trace_line`、`game_get_power` 拼。

所以方法层的价值不是「多几个查询」，而是让同一片区域只定义一次，然后被统计、截图、存蓝图、做 tether 复用。

### 1.4 归属与运动是两个轴

“垃圾块没有归属”这个观察很关键，但它说明的是：表里除了「动不动」，还混了另一条轴——**归属**。

- **归属**：这个对象由哪个固定点/实体拥有；它决定解析路径、生命周期和丢失判定。
- **运动**：位置是否随时间变化。

两条轴合起来是四象限：

| | 静止 | 运动 |
| --- | --- | --- |
| **有归属** | 建筑、矿脉、植被、黑雾建筑（归属行星/巢穴/基地） | 无人机、运输船、火箭、战斗单位（归属玩家/站点/机甲/舰队/巢穴/基地/发射井/戴森节点） |
| **无归属** | 世界坐标、行星坐标（它们不是对象，是参考系） | 垃圾块、玩家（观察者）、未来的投射物/碎片 |

所以：

- 建筑/矿脉/植被/黑雾建筑 = **有归属的定点**。
- 无人机/运输船/火箭/战斗单位 = **有归属的动点**。
- 垃圾块 = **无归属的动点**，不是定点。
- 玩家 = **无归属的动点**（观察者）；你之前没把它算进去，所以觉得垃圾块是唯一例外。
- 世界/行星坐标 = **无归属的静止参考系**，不是“对象”。

结论：两个页应该按**运动**分，另加一列**归属**。垃圾块放动点，归属填「无」；如果坚持放定点，只能把它定义成「某个 tick 的快照」，但这会掩盖它会动的事实，也会让「定点」这个词同时表示“静止对象”和“对象类别”。

## 2. 数据模型

### 2.1 坐标、时间、单位

| 名称 | 表示 | 说明 |
| --- | --- | --- |
| `universe` | `VectorLF3`，米 | 银河坐标系；恒星 `uPosition` 基本固定，行星 `uPosition` 随时间变化 |
| `planet_local` | `Vector3`，米 | 行星局部坐标，原点在行星中心；建筑 `EntityData.pos` 用这个 |
| `surface` | `lat` / `lon` / `alt`，度/米 | 行星表面坐标；径向投影到 `realRadius` |
| `t` | `gameTick`，整数 | 60 tick/秒；默认当前 tick |

- 输出精度：经纬度与现有 `Location` 一致，3 位小数；需要更细时最多 6 位，但不要声称超出游戏 `float` 精度。距离 0.1 米；时间精确到 tick。
- 单位统一用米/秒/度；不要混用 `AU` / `LY`，需要时在输出里单独给。
- 所有坐标转换必须调用游戏自己的方法，不要自己重写轨道/自转公式：
  - 当前帧：`PlanetData.uPosition`、`PlanetData.runtimeRotation`；
  - 未来帧：`PlanetData.PredictUPose(double)` / `PredictPose(double)`；
  - 玩家：`Player.uPosition`、`Player.uVelocity`、`Player.planetData`；
  - 恒星：`StarData.uPosition`；
  - 天体的预测时间基准在实现前必须用 `uPosition` 对照校验，不能凭方法名猜。

**坐标转换**：

```text
surface -> planet_local:  GameToolFormat.PositionFromLatLon(planet, lat, lon, alt)
planet_local -> universe: planet.uPosition + planet.runtimeRotation * local
universe -> planet_local: planet.runtimeRotation.Inverse() * (u - planet.uPosition)
planet_local -> surface:  GameToolFormat.Location(planet, local)
```

未来时刻 `t` 把 `uPosition` / `runtimeRotation` 换成 `PredictUPose(t)` 的结果。

### 2.2 区域 `Region`

统一 JSON 外形：

```json
{ "kind": "region", "type": "planet_patch", "planetId": 5, "latMin": -10, "latMax": 10, "lonStart": 100, "lonSpan": 30 }
```

十种区域 + 一个扩展类型：

| `type` | 字段 | 身份 |
| --- | --- | --- |
| `system` | `starId` | 恒星系 |
| `star` | `starId` | 恒星 |
| `planet` | `planetId` | 行星 |
| `grid` | `planetId`, `networkId` | 电网 |
| `factory` | `planetId`, `networkId`, `componentKey` | 工厂 |
| `hive` | `starId`, `hiveAstroId` | 太空黑雾巢穴 |
| `df_base` | `planetId`, `baseId` | 地面黑雾基地 |
| `dyson` | `starId`, `layerId?` | 戴森球；省略 `layerId` 表示整球 |
| `world_box` | `min`, `max` | 银河 AABB |
| `planet_patch` | `planetId`, `latMin`, `latMax`, `lonStart`, `lonSpan` | 行星表面经纬度矩形 |
| `sphere`（扩展） | `center`（Point）, `radius` | 以某个点为球心的球；用于「玩家附近 60m」 |

`sphere` 不在原表的十类里，但它是「附近」查询和现有 `game_analyze_area(radius)` 的自然抽象；建议作为扩展类型加入。

**身份与失效**：

- `system` / `star` / `planet`：`starId` / `planetId` 在同一个存档内稳定。
- `grid`：`networkId` 是运行期 ID，电网重建后可能变化；使用前用 `region.of(entity)` 重新解析。
- `factory`：`componentKey` 用连通分量内最小 `entityId` 或成员哈希；分量合并/拆分后必须视为失效，不能拿旧 key 继续查。
- `hive` / `df_base` / `dyson`：运行期对象 ID；读档后必须重新解析。
- `world_box` / `planet_patch` / `sphere`：纯描述，跨读档可保留；但 `planetId` 在新游戏里会指向别的行星，使用前校验 `epoch`。
- 所有运行期区域带 `epoch`（mod 在每次读档/新游戏时递增）。`epoch` 不匹配返回 `epoch_mismatch`。

### 2.3 定点 `Point`

表格里的「定点」按对象类别分，不是按绝对静止分。`type` 直接采用表里的名字，减少模型翻译成本。

| `type` | 字段 | 语义 |
| --- | --- | --- |
| `surface` | `planetId`, `lat`, `lon`, `alt?` | 行星坐标；固定在行星表面 |
| `universe` | `x`, `y`, `z` | 世界坐标；固定在银河系 |
| `building` | `planetId`, `entityId`, `offset?` | 建筑中心；`EntityData.pos` |
| `vein` | `planetId`, `veinId` | 矿脉节点；`VeinData.pos` |
| `vegetation` | `planetId`, `vegeId` | 植被/石块/冰；`VegeData.pos` |
| `df_space_building` | `starId`, `hiveId`, `enemyId` | 太空黑雾建筑；`SpaceSector.enemyPool` |
| `df_ground_building` | `planetId`, `enemyId` | 地面黑雾建筑；`PlanetFactory.enemyPool` |
| `trash` | `trashId` | 垃圾块当前快照；`TrashData.lPos` / `uPos` |
| `celestial`（扩展） | `body`（`star`/`planet`）, `id` | 天体中心；表里没有，但 `sphere` / `region.of` 需要 |

```json
{ "kind": "point", "type": "surface", "planetId": 5, "lat": 3.2, "lon": 101.5, "alt": 0 }
{ "kind": "point", "type": "universe", "x": 1200.0, "y": 35.0, "z": -800.0 }
{ "kind": "point", "type": "vein", "planetId": 5, "veinId": 42 }
{ "kind": "point", "type": "trash", "trashId": 7 }
```

说明：

- 「矿脉」是节点，不是矿脉群；一个矿脉群有多个 `veinId`。要按群处理时加 `veinGroupId` 过滤（P1）。
- `building` / `vein` / `vegetation` / `df_*` / `trash` 的 id 来自不同池，不能互用；运行期 id 会回收，必须带 `epoch` 并校验 `stale`。
- 太空黑雾建筑虽然叫「定点」，但它在宇宙系里随巢穴轨道运动；`at(t)` 求值，`contains` / `distance` 用当前 tick，不能当绝对静止。
- 垃圾块也有 `uVel` / `uAgl` / `life` / `landPlanetId`，会漂移或坠落；`point.trash` 只给当前快照，跟踪用 `motion.trash`，不要把它当固定坐标。

### 2.4 动点 `Motion`

表格里的「动点」是 10 类具体目标；统一用 `Motion` 表示，`type` 直接采用表里的名字。

| `type` | 字段 | 数据源（设计名） | 帧 |
| --- | --- | --- | --- |
| `player` | `playerId?` | `Player.uPosition` / `uVelocity` / `planetData` | 行星/宇宙 |
| `construction_drone` | `planetId`, `craftId` | `PlanetFactory.craftPool`，`prototype=ConstructionDrone` | 行星 |
| `delivery_drone` | `planetId`, `courierId?` | `PlanetTransport.courierRenderer.couriersArr` / `DeliveryPackage` | 行星 |
| `logistics_drone` | `planetId`, `stationId`, `index?` | `StationComponent.workDroneDatas` / `droneRenderer` | 行星 |
| `logistics_ship` | `stationGid`, `index?` | `StationComponent.workShipDatas` / `shipRenderer` | 宇宙 |
| `dyson_rocket` | `starId`, `rocketId` | `DysonSphere.rocketPool` | 宇宙 |
| `combat_drone` | `planetId`, `unitId?` | `CombatGroundSystem.units` → `CraftData` | 行星 |
| `warship` | `fleetId?` | `CombatSpaceSystem.fleets` → `CraftData` | 宇宙 |
| `df_space_unit` | `enemyId` | `SpaceSector.enemyPool`，`isSpace` | 宇宙 |
| `df_ground_unit` | `planetId`, `enemyId` | `PlanetFactory.enemyPool`，`isSpace=false` | 行星 |
| `trash` | `trashId` | `TrashSystem.container.trashDataPool` | 行星/宇宙 |
| `celestial`（扩展） | `body`, `id` | `PlanetData` / `StarData` | 宇宙 |
| `track` | `target`, `samples[]`, `validFrom`, `validTo`, `model` | — | — |

说明：

- 字段名是设计名；具体 id 由 mod 解析器校验。`stationId` / `entityId` / `enemyId` / `trashId` 不要混用。
- 星际船的 `stationGid` 用 `StationComponent.gid`（全局）；行星内无人机用 `planetId` + 本地 `stationId`。不要混用 `id` 和 `gid`。
- `delivery_drone` / `logistics_drone` 的位置来自 `begin` / `end` / `t` 插值，`model=interpolated`；不要当成精确物理位置。
- `trash` 在表里属于定点，但它是动态对象；提供 `motion.trash` 只是为了跟踪。受重力/落地影响，不提供 `predict`，只给 `state` / `track`。
- `celestial` 是扩展，用于行星/恒星中心；表里没有，但 `sphere` / `eta` 需要。
- `player` 在行星表面时用行星局部帧；在太空时用宇宙帧。`state` 的 `frame` 字段说明当前是哪一种。

`state` 的统一返回：

```json
{
  "tick": 123456,
  "frame": "planet",
  "planetId": 5,
  "lat": 3.2,
  "lon": 101.5,
  "alt": 0.0,
  "position": { "x": 1, "y": 2, "z": 3 },
  "velocity": { "x": 0, "y": 0, "z": 0 },
  "model": "constant_velocity",
  "validity": "valid"
}
```

`validity` 只取 `valid` / `stale` / `lost` / `unloaded` / `unsupported`，不引入打分或置信度。`model` 只取 `sampled` / `interpolated` / `constant_velocity` / `orbital`，让调用方知道预测依据。

### 2.5 统一外形

```text
SpatialValue =
  Region  { kind:"region",  type, ... , epoch? }
  Point   { kind:"point",   type, ..., parent?: SpatialRef, context?: Region, epoch? }
  Motion  { kind:"motion",  type, ..., parent?: SpatialRef, context?: Region, epoch? }
```

`kind` 决定方法分派；`type` 决定构造/解析；`epoch` 决定运行期身份是否还有效。

**`parent` 与 `context` 不是一回事**：

- `parent`：点状归属，例如无人机→站点、黑雾单位→巢穴、火箭→发射井/戴森节点；自由对象（垃圾块、玩家、投射物）没有 `parent`。
- `context`：当前所在区域，例如行星或恒星系；垃圾块没有 `parent`，但有 `context`（行星/太空），用来决定求值帧。
- `parent` 是解析路径和生命周期依据：站点拆了，无人机就 `lost`；`context` 只说明“现在在哪”。
- 没有 `parent` 不代表静止：垃圾块、玩家都是无归属动点。

下面 §2.3 / §2.4 的类型表省略了 `parent` / `context`；它们对所有 Point / Motion 都适用。

所有空间参数都允许写成 `{"ref":"变量名"}`，由 sidecar 的变量表展开；展开后再校验。

**用描述，不用服务端句柄**：描述可以进 prompt、可以写进 `run_script`、可以重放；句柄跨会话失效，也无法让模型检查内容。运行期身份靠 `epoch` + 每次重新解析，而不是长期句柄。
在 `run_script` 中，所有 `t` 必须显式传入；`now` 只用于交互式工具调用，不能进脚本，否则重放不一致。

- `contains(factory, point)` → `unsupported_capability`，提示用 `members` / `nearestMember`。
- `stats(system)` → 可以返回行星数与汇总，但不把不同行星的功率直接相加；返回 `byPlanet`。

**`stats` 的口径**：

- `stats(grid)` 用 `PowerNetwork` 的 `energyRequired` / `energyServed` / `energyCapacity` / `energyStored`，与电网面板对齐。
- 其他区域的 `stats` 用成员实体的 `requiredEnergy` 聚合，与 `game_analyze_area` 对齐。
- 不要把两种口径混在同一个数字里；结果里用 `basis` 标明 `network` 或 `entities`。

- `stats` 的配方/功率只对玩家建筑有意义；矿脉、植被、黑雾建筑、单位只计数，不进 `byRecipe` / `powerKw`。

**`filter` 的统一字段**：

```json
{ "kind": "building|vein|vegetation|df_space_building|df_ground_building|trash|player|unit", "category": "assembler", "protoId": 2303, "protoName": "组装机", "recipeId": 1 }
```

多个条件是 AND；`kind` 不传时按区域类型给默认值（行星默认 `building`，黑雾基地默认 `unit`）。物流站/仓储等细分用 `category`，不要塞进 `kind`。

## 4. 关键语义

### 4.1 行星区域（经纬度矩形）

定义：

- 构造函数可以接受「两个角点」，但内部规范成 `latMin` / `latMax` / `lonStart` / `lonSpan`；这样跨 ±180° 时没有「短弧还是长弧」的歧义。
- 两个角点输入时，按 `lonStart = 第一个角点.lon`、`lonSpan = normalize(第二个角点.lon - 第一个角点.lon)` 取向东跨度；要反向就交换两个点，或直接给 `lonStart` / `lonSpan`。
- `latMin < latMax`，范围 `[-90, 90]`。
- `lonStart` 规范到 `[-180, 180)`；`lonSpan ∈ (0, 360]`。
- `lonSpan = 360` 表示整条纬度带。
- 经度按 `lonStart` 向东计算，允许跨 ±180°；因为存的是起点 + 跨度，不存在「短弧还是长弧」的歧义。
- 边界包含：`lat == latMin`、`lat == latMax`、经度恰好落在两端都算在内。

包含判定：

```text
if (p.planetId != r.planetId) return false
lat = p.lat
lon = normalize(p.lon)
if (lat < r.latMin || lat > r.latMax) return false
d = normalize(lon - r.lonStart)   // [0, 360)
return d <= r.lonSpan
```

投影：

- 所有点按径向投影到行星表面，`alt` 不参与包含判断。
- 包含判定用 `EntityData.pos` 的原始局部坐标算经纬度，不要用输出里四舍五入后的 `Location`；否则边界点会因为格式化翻转。
- 行星中心 `lat/lon` 未定义，返回 `false`。
- 极点：若 `latMin <= ±90 <= latMax`，极点处所有经度都算包含；不要用 `atan2(0,0)` 得到随机经度。
- 其他行星上的点即使宇宙位置在附近，也不属于该行星区域。

距离：

- 点在区域内：0。
- 点在区域外：到最近边界弧的大圆距离；P1 实现，允许用采样 + 局部细化，但输出必须带 `method`，不能声称精确。
- 跨极点的区域距离先不做精确解，返回 `unsupported` 或近似值并标注。

相交：

- 纬度区间重叠，且两个经度弧有交集；跨 ±180° 时先拆成最多两段再比。
- P1 实现；不要用外接矩形代替。

### 4.2 世界区域（银河 AABB）

- `min` / `max` 每个轴 `min < max`；坐标系是银河系 `VectorLF3`。
- **先区分两种“世界坐标”**：DSP 里 `VectorLF3` 是银河系坐标，跨行星稳定；行星局部的 `Vector3`（建筑 `EntityData.pos`）会随行星自转，不能直接当成跨行星的世界坐标。`world_box` 只接受前者；如果要后者，另设 `planet_box`（`planetId` + 局部 AABB + `epoch`），不要复用 `world_box`。
- `contains(p, t)`：把 `p` 在 `t` 时刻转到 `universe`，再做 AABB 判定。
- **时间相关性**：表面定点会随行星自转/公转进出盒子；同一个经纬度在不同 tick 可能得到不同结果。这是正确行为，但必须在输出里带 `tick`，并在提示词里说明。
- `members(r)`：遍历已加载行星的实体，把位置转到 `universe` 后过滤；未加载的星球无法枚举，返回 `partial=true` 和 `missingPlanets`。
- 如果用户其实想要「某恒星系局部坐标的盒子」，应增加 `system_box`（以恒星为原点、轴向固定），不要复用 `world_box`。这一点需要确认（见 §9）。

### 4.3 电网

成员判定分两层：

1. **有电力组件的建筑**：`entity.powerConId` / `powerGenId` / `powerAccId` / `powerExcId` 对应的 `networkId == N`。
2. **被电网覆盖但不耗电的建筑**：`PowerNodeComponent` 有 `networkId`、`powerPoint`、`coverRadius`；把该网络所有节点的覆盖球并起来，建筑位置落在任一球内就算成员。

算法：

```text
nodes = powerSystem.nodePool 中 networkId == N 的节点
for each entity:
    if entity 的任一 power 组件 networkId == N: include
    else if 存在 node 使 distance(entity.pos, node.powerPoint) <= node.coverRadius: include
```

注意：

- `coverRadius` 是游戏字段，是否与 UI 的「电网覆盖」完全一致需要实机核对；多层建筑/附加建筑可能要用 `GetObjectPosition` 或 `alt`。
- `contains(point)` 不支持；电网是集合，不是空间体。
- `stats(grid)` 直接读 `PowerNetwork` 的 `energyRequired` / `energyServed` / `energyCapacity` / `energyStored`，不要用成员建筑的 `requiredEnergy` 重新加一遍，否则会和面板对不上。

### 4.4 工厂

定义：**同一电网内**、由传送带/分拣器连通的建筑群。若一个连通群跨两片电网，则它属于两座工厂——所以工厂身份必须带 `networkId`。

算法：

1. 取该电网的成员建筑集合 `S`。
2. 在 `S` 内建无向图：
   - 分拣器：`pickTarget <-> insertTarget`；
   - 传送带：`belt.entityId <-> outputId / backInputId / leftInputId / rightInputId`。
3. 并查集求连通分量；成员数 ≥ 2 的分量才算工厂。
4. `componentKey` = 分量内最小 `entityId`；`fingerprint` = 排序后成员 id 的哈希。
5. `factory` 区域 = `(planetId, networkId, componentKey)`；查询时重新计算并比对 `fingerprint`，不一致返回 `stale`。

说明：

- 单栋建筑如果没有传送带/分拣器连接，不构成工厂；不要把它包装成「只有一个成员的工厂」。
- 工厂没有 `contains(point)`；用 `members`。
- `stats(factory)` 复用 `analyze_area` 的配方聚合，不要重写一份。
- 缓存键：`(planetId, networkId, entityVersion)`；监听 `onBuild` / `onDismantle` 或每 tick 比对 `entityCursor`，失效即重建。
- 复杂度 O(E α)；10k 建筑量级可接受，但查询要设 `maxNodes` 并返回 `truncated`。

### 4.5 恒星系 / 恒星 / 行星

- **恒星系**：`StarData.systemRadius` 为半径；`members` = `star.planets`（含未加载的轨道信息）；`contains` 优先按 `starId` 判定，自由宇宙点再按距离。
- **恒星**：`StarData.radius`（视觉）与 `physicsRadius`（物理）可能不同；输出两个值，`contains` 默认用 `radius`，并在结果里标 `radiusKind`。
- **行星**：`realRadius + atmosphereHeight` 为上界；`contains` 要求 `planetId` 相同且 `0 <= localRadius <= 上界`。低于地表的点（洞穴/矿脉）也算在行星内。
- **成员**：行星的 `members` 包括建筑、矿脉、植被、玩家、黑雾基地/单位；按 `filter` 裁剪，默认只返回建筑，避免一次拉太多。

### 4.6 动点

#### 4.6.1 目标目录与数据源

| 目标（`type`） | 数据源 | 帧 | 位置/速度 | `predict` | 备注 |
| --- | --- | --- | --- | --- | --- |
| `player` | `Player.uPosition` / `uVelocity` / `planetData` | 行星/宇宙 | 精确 | 短时匀速，≤2s | 在太空时 `planetData` 为空，用宇宙帧 |
| `construction_drone` | `PlanetFactory.craftPool`，`CraftData.prototype=ConstructionDrone` | 行星 | `pos` / `vel` | 短时匀速，≤5s | 只列活跃 drone；停机/在机甲内时可能无位置 |
| `delivery_drone` | `PlanetTransport.courierRenderer.couriersArr`（`CourierData`）/ `DeliveryPackage` | 行星 | `begin`/`end`/`t` 插值 | 不提供 | `model=interpolated`；不是精确物理位置 |
| `logistics_drone` | `StationComponent.workDroneDatas` / `droneRenderer`（`DroneData`） | 行星 | `begin`/`end`/`t` 插值 | 不提供 | 同上；按 `stationId` 找 |
| `logistics_ship` | `StationComponent.workShipDatas`（`ShipData`） | 宇宙 | `uPos` / `uVel` | 短时匀速，≤5s；跃迁时禁止 | `warpState>0` 时只给 `state` |
| `dyson_rocket` | `DysonSphere.rocketPool`（`DysonRocket`） | 宇宙 | `uPos` / `uVel` | 短时匀速，≤5s | 按 `starId` 找；目标节点可能已建成 |
| `combat_drone` | `CombatGroundSystem.units`（`UnitComponent`）→ `CraftData` | 行星 | `pos` / `vel` | 短时匀速，≤2s | `owner` / 编队行为会改变路径 |
| `warship` | `CombatSpaceSystem.fleets`（`FleetComponent`）→ `CraftData` | 宇宙 | `pos` / `vel` | 短时匀速，≤2s | 舰队编队/跃迁会改变路径 |
| `df_space_unit` | `SpaceSector.enemyPool`，`EnemyData.isSpace`，`unitId` | 宇宙 | `pos` / `vel` | 短时匀速，≤2s | 只取 `unitId>0` 的单位，不取建筑 |
| `df_ground_unit` | `PlanetFactory.enemyPool`，`EnemyData.isSpace=false`，`unitId` | 行星 | `pos` / `vel` | 短时匀速，≤2s | 同上；用行星局部坐标 |
| `trash` | `TrashSystem.container.trashDataPool`（`TrashData`） | 行星/宇宙 | `lPos` 或 `uPos` / `uVel` | 不提供 | 受重力/落地影响；`life>0` 才算活跃 |
| `celestial`（扩展） | `PlanetData` / `StarData` | 宇宙 | `PredictUPose` | 轨道，分钟级 | 用于 `sphere` / `eta` 的参考中心 |

**归属（`parent`）**：

| 目标 | `parent` | 说明 |
| --- | --- | --- |
| `player` | 无 | 观察者；`context` 是当前行星/太空 |
| `construction_drone` | 玩家/机甲 | 建造目标也可作为归属；没有就按玩家 |
| `delivery_drone` | 玩家/配送包 | 玩家配送系统 |
| `logistics_drone` | 站点 | 站点拆了，无人机就 `lost` |
| `logistics_ship` | 站点 | 站点拆了，运输船就 `lost` |
| `dyson_rocket` | 发射井/戴森节点 | 目标节点可能已建成 |
| `combat_drone` | 机甲/舰队 | 编队行为会改变路径 |
| `warship` | 舰队 | 舰队编队/跃迁会改变路径 |
| `df_space_unit` | 巢穴 | 巢穴被毁，单位 `lost` |
| `df_ground_unit` | 基地 | 基地被毁，单位 `lost` |
| `trash` | 无 | 只有 `context`（行星/太空），没有点状归属 |
| `celestial` | 无 | 参考中心，不是“被谁拥有” |

`parent` 不存在时，解析器必须走全局池（例如 `TrashSystem.container`），不要猜一个归属；这也是垃圾块和无人机的实现差异。

#### 4.6.2 目标获取

- 单个目标用 `motion.<target>(...)` 构造；批量找目标用 `motion.list(kind, region?, limit?)`。
- `player` 是单例，`list` 返回一项。
- `construction_drone` / `combat_drone` / `df_ground_unit` 用 `planetId` + 活跃池；`region` 可以限定范围。
- `logistics_drone` / `logistics_ship` 先通过 `region.members` 或 `game_get_logistics` 找到 `stationGid`（星际船）或 `planetId` + `stationId`（行星无人机），再用 `workDroneDatas` / `workShipDatas` 下标取；不要让模型猜下标。
- `dyson_rocket` 用 `starId` + `rocketId`；`rocketPool` 只含活跃火箭。
- `df_space_unit` / `df_ground_unit` 用 `enemyId`；`EnemyData.unitId > 0` 才是单位。
- `trash` 用 `trashId`；只取 `life>0` 的项。`landPlanetId` / `lPos` 表示已落地或接近行星，`uPos` 表示太空；同一 `trashId` 可能在两种帧之间切换。
- 有 `parent` 的目标优先从 parent 的子池解析（station→`workDroneDatas`、hive→`units`、base→`enemyPool`、fleet→`units`）；没有 `parent` 的（trash/player）走全局池或单例。
- `motion.list` 返回 `{ type, id, parent, context, state }` 摘要，不返回完整轨迹；后续要轨迹再 `track`。

#### 4.6.3 采样与预测

- `track` 是 `IGameToolJob`：在 `durationTicks` 内每 `intervalTicks` 采样一次，单次调用最多 600 tick（10 秒）/ 120 样本；必须用 `Step(budgetMs)` 分帧，不能阻塞主线程。
- 可选优化：mod 维护玩家和最近跟踪目标的环形缓冲（最近 600 tick，每 6 tick 一个样本），`track` 查过去窗口时直接读缓冲；任意目标按需开启采样。P2 再做。
- `state` 的 `velocity`：玩家用 `uVelocity`；`CraftData` / `EnemyData` 用 `vel`；`ShipData` / `DysonRocket` 用 `uVel`；`TrashData` 用 `uVel`；`CourierData` / `DroneData` 没有可靠速度，用最近两帧差分或省略，并标 `model=interpolated`。
- `predict`：
  - `celestial`：`PredictUPose(t)`，`model=orbital`；
  - 有 `pos/vel` 的目标：匀速外推，`model=constant_velocity`，地平线见 4.6.1；
  - `track`：按样本线性插值，`model=sampled`，不外推到 `validTo` 之后；
  - `interpolated` 目标：不提供 `predict`，只给 `state` / `track`；
  - `trash`：受重力和落地影响，不提供 `predict`，只给 `state` / `track`。
- `eta`：按 `intervalTicks` 前向采样，逐点做 `contains`；返回首次命中的 tick 和点；到 `horizonTicks` 仍未命中返回 `null`，不要返回「大概会到」。
- `closest`：同样采样；天体可解析，但先统一采样，保证语义一致。
- `lost`：目标 ID 无效、`parent` 被毁（站点/巢穴/基地/舰队）、`context` 未加载、火箭已到节点、垃圾块被清除/落地都算 `lost`；返回最后已知位置 + `lastSeenTick`，不要静默换成玩家位置。

#### 4.6.4 帧与坐标

- 行星局部的目标：`CourierData.begin/end`、`DroneData.begin/end` 是行星局部；先转 `surface` / `universe` 再输出。
- `CraftData.pos` / `EnemyData.pos` 是 `VectorLF3`；先看 `isSpace` / `localized` / `astroId`，再用 `SpaceSector.InverseTransformToAstro` 转行星局部，不能凭字段类型直接当 `Vector3`。
- 宇宙目标：`ShipData.uPos` / `DysonRocket.uPos` / `TrashData.uPos` / `SpaceSector.enemyPool` 的 `EnemyData.pos` 是宇宙坐标；不要直接当行星局部。
- `trash`：太空段用 `uPos` / `uVel`，再入/落地后用 `lPos`（`landPlanetId` 指向行星）；`frame` 必须随 `state` 返回，`point.trash` 的快照也要标 `frame`。
- `state` 同时给 `frame`、`planetId`（如果能确定）、`position`、`velocity`；行星局部时再给 `lat/lon/alt`。
- 同一目标在不同 tick 可能切换帧（玩家从行星起飞、运输船跃迁、黑雾单位进出大气层、垃圾块坠落）；`frame` 必须随 `state` 返回，调用方不能假设固定。

### 4.7 精度、上限、截断

| 项 | 上限 | 行为 |
| --- | --- | --- |
| `members` | 默认 100，最大 2000 | 超出 `truncated=true` |
| `stats` 扫描 | 单次 10000 实体 | 超出 `truncated=true` |
| `track` | 600 tick / 120 样本 | 超出直接拒绝，不截断 |
| `motion.list` | 默认 50，最大 200 | 超出 `truncated=true` |
| `predict` 地平线 | `player` 120 tick（2s）；其他有速度目标 300 tick（5s） | 超出返回 `unsupported`；`celestial` 例外 |
| `world_box` 成员 | 只扫已加载行星 | `partial=true` + `missingPlanets` |
| `factory` 节点 | 默认 300，最大 2000 | 超出 `truncated=true` |
| 区域嵌套 | 最多 8 层 `subregions` | 超出拒绝 |

### 4.8 错误模型

| 错误码 | 场景 | 建议 |
| --- | --- | --- |
| `invalid_value` | 字段缺失/越界/`latMin >= latMax` | 返回具体字段 |
| `stale` | 实体 ID 被回收、工厂分量变化 | 重新 `region.of` / `members` |
| `epoch_mismatch` | 读档/新游戏后使用旧运行期区域 | 重新构造 |
| `unloaded` | 行星工厂未加载 | 先让玩家/游戏加载，或只给轨道信息 |
| `unsupported_capability` | 对工厂调用 `contains` | 用 `members` / `nearestMember` |
| `out_of_range` | 时间/距离/半径超限 | 缩小范围 |
| `unknown_time` | 历史时刻没有样本，或实体集合的历史查询 | 只能用 `now` 或已采样的 `track` |
| `partial` | 结果不完整 | 不是错误；调用方必须处理 |

每个错误带 `hint`，例如「工厂没有 Area 能力；用 members 取成员，再用 distance 到成员」。

## 5. 工具面

### 5.1 三个只读查询工具

不做一个 `space_eval` 表达式语言，也不做 30 个工具。按变量主语分三个工具，`op` 是动词：

| 工具 | `op` | 说明 |
| --- | --- | --- |
| `space_region` | `members`, `count`, `stats`, `contains`, `intersects`, `subregions`, `boundary`, `nearestMember`, `of`, `around`, `bbox`, `describe` | 区域构造与查询 |
| `space_point` | `distance`, `bearing`, `offset`, `nearest`, `locate`, `convert`, `project`, `describe` | 定点构造与度量 |
| `space_motion` | `list`, `state`, `track`, `predict`, `eta`, `closest`, `path`, `lost`, `describe` | 动点构造与跟踪 |

示例：

```json
{
  "op": "members",
  "region": { "kind": "region", "type": "planet_patch", "planetId": 5, "latMin": -10, "latMax": 10, "lonStart": 100, "lonSpan": 30 },
  "filter": { "category": "assembler" },
  "limit": 50
}
```

```json
{
  "op": "distance",
  "a": { "kind": "point", "type": "surface", "planetId": 5, "lat": 3.2, "lon": 101.5 },
  "b": { "kind": "region", "type": "planet", "planetId": 5 },
  "mode": "surface"
}
```

```json
{
  "op": "track",
  "target": { "kind": "motion", "type": "player" },
  "durationTicks": 120,
  "intervalTicks": 6
}
```

```json
{
  "op": "list",
  "kind": "logistics_ship",
  "region": { "kind": "region", "type": "system", "starId": 3 },
  "limit": 20
}
```

**Schema 建议**：

- `region` / `point` / `motion` 参数用 TypeBox 的 `Type.Union` 描述具体类型；不要用「一堆可选字段」让模型猜。
- `op` 用 `Type.Union([Type.Literal(...)])`；每个 `op` 的必填字段在 mod 侧再校验一次，防止 schema 漂移。
- 结果统一带 `{ "available": true, "gameTick": ..., "epoch": ..., "partial": false, "truncated": false, "data": ... }`。

### 5.2 复用行动工具

按 §3.7 给现有工具加 `region` / `point` 参数。优先级：

1. `game_analyze_area` + `region`：直接替代「中心 + 半径」和 `all`，是最高频的组合。
2. `game_capture_view` + `point/region`：截图取景不再要求模型自己算经纬度。
3. `game_tether_add` + `point`：方位指示直接接受定点。
4. `game_get_entities` + `region`：先过滤再分页，减少 token。
5. `game_render_layout` / `game_copy_blueprint` + `region`：布局图/蓝图不再要求模型给中心。

### 5.3 变量命名（P1）

如果希望跨回合引用「那片赤道产线」「那个黑雾基地」，加一个 `space_var` 工具：

| `op` | 参数 | 行为 |
| --- | --- | --- |
| `set` | `name`, `value` | 校验并保存；返回规范值 |
| `get` | `name` | 读取 |
| `list` | — | 列出名字、类型、摘要、`epoch` |
| `delete` | `name` | 删除 |

- 作用域：sidecar 会话；不写存档。
- 名字：`[a-z][a-z0-9_]{0,31}`；最多 32 个。
- 所有空间参数允许 `{"ref":"name"}`；sidecar 展开后再发给 mod。
- `epoch` 变化时，运行期区域/动点全部失效；纯几何描述保留但提示重新校验。
- 变量只存空间描述，不存密钥、不存任意 JSON。

### 5.4 提示词约束

- 「先构造/校验，不要手算经纬度；需要坐标就用 `space_*`。」
- 「`partial=true` 不是全量，回答里要说明缺了哪些行星/实体。」
- 「`unsupported_capability` 不是空结果；换 `members` / `nearestMember`。」
- 「区域默认 `contains` 是表面投影；`world_box` 的成员随时间变化，必须带 tick。」
- 「动点预测只对天体和短时实体有效；超过 horizon 返回 `null` 时不要编造到达时间。」
- 「分析一片区域时优先传 `region`，不要同时传 `center/radius`。」

### 5.5 三条典型链路

**「把赤道这片产线存成蓝图」**

```text
r = region.planetPatch(planetId=5, latMin=-5, latMax=5, lonStart=95, lonSpan=30)
m = region.members(r, filter={category:"assembler"}, limit=500)
stats = region.stats(r)
blueprint = game_copy_blueprint(region=r, name="赤道-铁块线")
```

模型只需要给经纬度边界；成员枚举、配方统计、蓝图范围都由同一份区域成员集合驱动，不会出现「统计了一片、蓝图存了另一片」。

**「玩家附近 60 米有什么」**

```text
me = motion.player()
p = freeze(me, now)
r = region.sphere(center=p, radius=60)
members = region.members(r, limit=40)
stats = region.stats(r)
```

`sphere` 在宇宙系里求值；如果玩家在行星表面，等价于以玩家为中心的三维球，不会像现有 `analyze_area` 那样在极点附近按 XZ 平面切出偏差。

**「这个黑雾基地会不会打到我」**

```text
b = region.dfBase(planetId=5, baseId=12)
units = region.members(b, filter={kind:"unit"})
m = motion.dfGroundUnit(planetId=5, enemyId=units[0].id)
me = freeze(motion.player(), now)
r = region.sphere(center=me, radius=30)
eta = space_motion(op="eta", target=m, region=r, horizonTicks=600)
```

如果单位没有可靠路径模型，`predict` 返回 `unsupported`，`eta` 只基于已采样轨迹；回答里要明确「按当前轨迹」而不是「一定会到」。

## 6. 实现分层

### 6.1 文件布局

```text
mod/src/Shared/Spatial/          // Unity-free；只放描述、校验、纯数学
  SpatialValue.cs
  SpatialJson.cs
  GeoMath.cs                     // Vec3d/Quatd、经纬度、球面距离、AABB
mod/src/IcarusII/Game/Spatial/   // 运行时解析；可用 UnityEngine
  PlanetFrame.cs                 // surface/local/universe + PredictUPose 缓存
  RegionResolver.cs              // 十种区域 + sphere 的分派
  GridRegion.cs                  // 电网成员/覆盖
  FactoryRegion.cs               // 并查集/缓存
  PointCatalog.cs                // building/vein/vegetation/trash/df_* 的解析
  MotionCatalog.cs               // 10 类动点 + trash/celestial 的数据源/list 适配
  MotionSampler.cs               // state/track/predict/eta
  SpatialJob.cs                  // track 的分帧 job
mod/src/IcarusII/Game/Tools/
  SpatialTools.cs                // 3 个只读工具
sidecar/src/spatial/
  schema.ts                      // TypeBox 描述 + 错误
  vars.ts                        // 命名变量表
  format.ts                      // 结果裁剪/展示
```

`mod/src/Shared` 不能引用 `UnityEngine`；所以 `SpatialValue` 和 `GeoMath` 用自己的 `Vec3d` / `Quatd`，在 mod 边界转成 `Vector3` / `Vector3LF3`。这样协议测试和纯数学测试可以离线跑。

### 6.2 数据流

1. 模型调用 `space_region` / `space_point` / `space_motion`。
2. sidecar 校验 schema，展开 `{"ref":...}`，把规范 JSON 发给 mod。
3. mod 在主线程解析：
   - 构造 `SpatialValue`；
   - `resolve` 检查 `epoch` / `stale`；
   - 需要未来时刻时调用 `PredictUPose`；
   - 查询 `PlanetFactory` / `PowerSystem` / `DysonSphere`。
4. mod 返回 `data + meta`（`gameTick`、`epoch`、`partial`、`truncated`）。
5. sidecar 裁剪/格式化，必要时把大列表分页。

### 6.3 性能

- 球体/附近查询优先用 `PlanetFactory.hashSystemDynamic.GetEntitiesInAreaNonAlloc`，不要每次线性扫全星球。
- 行星区域：建筑 `EntityData.pos` 已在手，直接算经纬度过滤；10k 量级线性扫描可接受，按 tick 缓存结果。
- 世界区域：遍历已加载行星；每个实体转 `universe`；没有全局空间哈希，必须设上限并返回 `partial`。
- 工厂：并查集 + 按 `(planetId, networkId, entityVersion)` 缓存；监听 build/dismantle 或比对 `entityCursor`。
- 行星姿态：按 tick 缓存 `PredictUPose` 结果，避免同一查询里反复算。
- `stats` 的配方/功率聚合从 `AnalyzeAreaTool` 抽成共享函数，按实体 id 集合输入；区域查询只负责选 id，不重写聚合。
- 动点查询只扫目标池：物流无人机扫 `droneRenderer`，配送扫 `courierRenderer`，火箭扫 `rocketPool`，黑雾单位扫 `enemyPool`，垃圾块扫 `trashDataPool`；不要为了 `list` 全扫 `CraftData`。
- 热路径不要 LINQ；复用 `List<int>` / 数组；结果序列化前再裁剪。

### 6.4 协议

- 先改 [protocol-v1.md](../protocol-v1.md)，再改 `mod/src/Shared/Protocol/Protocol.cs`、`sidecar/src/protocol.ts` 和测试。
- 只加可选字段/新工具名，不改 v1 既有字段语义；旧端忽略 `region` / `point` 参数即可。
- `game_analyze_area` 的 `region` 与 `center/radius/all` 互斥；同时传返回 `invalid_value`，不要静默选一个。
- 工具结果新增 `epoch` / `partial` / `truncated` 可选字段；旧端不读也不影响。
- `space_*` 全部只读，`risk=0`；行动工具沿用原有 risk/确认/撤销。

### 与本节前文的口径差异

- **`navigation` 由 `game_tether_add` 承接**：矩阵里的导航行是写操作，
  放在只读工具里会破坏 `risk=0` 的约定。`game_tether_add` 新增 `space` 参数，
  直接接 `space_*` 的 `kind`/`type`/`target`：区域折到落点行星或首座建筑，
  定点折到建筑/矿脉/行星；动点会移动，静态箭头无法表示，直接拒绝。
- **不做 `contains` / `intersects` 布尔运算**：成员枚举（`list`）已覆盖“某片区域里有什么”，
  布尔判定留到有真实需求时再加，避免先造一套没人调用的几何 API。
- **不做 `predict` / `eta` / `track`**：动点只给当前 tick 的快照（`location` + `information`）。
  跨 tick 追踪需要环形缓冲与分帧 job，等有“还有多久到”的实际提问再加。
- **不做 `space_var` 命名变量**：`target` 直接接受 id，跨回合引用由对话历史承担。
- **不做 `sphere` 类型**：球体查询目前用 `world_box` + `radius` 的近似，或在
  `game_analyze_area` 里继续用原有的球心 + 半径。
- **`input` / `output` 与 `production` / `consumption` 共用生产桶**：
  游戏的 `TrafficStatistics` 是行星级且不分方向的，无法按建筑子集切分；
  两者都读 `ProductionStatistics` 的产出/消耗两列，已在工具结果里写明“不可相加”。
- **`basis=installed` 只对 `production` / `consumption` 开放**：物流进出没有“理论物流”，
  传了会明确报错而不是静默降级。
- **蓝图只读文件，不落到存档**：`list` 给建筑台数、`input`/`output`/`production`/`consumption`/`power`
  给按配方与原型算的理论值、`information` 给作者/版本/缩略图图标与布局、`note` 给介绍、`parent` 给父目录；
  `location` / `navigation` 对它不适用（蓝图没有空间位置）。
  路径复用 `BlueprintActions` 的沙箱：必须落在游戏蓝图根内，否则报错。

### 实现期发现并修掉的坑

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| `consumption` 返回的是生产速度 | 生产桶按物品存，产出/消耗是同一 stat 的两段；之前一律取产出段 | 按方向取对应段 |
| 纯消耗品（燃料、弹药）整条漏掉 | 遍历只看产出侧的物品集合 | 产出与消耗两侧取并集 |
| 世界区域 storage 空引用、flow/power 误报「工厂未加载」 | 世界区域横跨多颗行星，`target.Planet` 为 null | 按 `planetId` 分组后各自查询再合并 |
| 世界区域 partial 永远为 false | 扫描集合与已加载集合同源，`planets > loaded.Count` 不可能成立 | 改按「落在区域内但工厂未加载」的行星计数 |
| 黑雾建筑会把会移动的单位当建筑返回 | 敌人池里建筑与单位混在一起，只按 `isSpace` 过滤 | 按 `dynamic` 区分，传错时提示改用 `space_motion` |
| 玩家低空飞行时被当成离开行星 | 判定写成 `movementState == Walk`，`Drift`（悬停）也是行星态 | 与 `TetherTools` 统一为 `< Fly` |
| 动点 storage 的空结果冒充「什么都没带」 | 只有物流无人机能从 craft 池取货 | 补 hint 说明建设无人机/配送机的货不在那里 |
| storage 结果带 `window: 10分钟` | 复用统计头 | 存量单独标 `kind=stock` |
| `SpatialException` 被报成 `internal` | 分帧任务在 `Finish()` 才抛，那里一律按内部错误处理 | 新增 `ArgumentErrorException`，分发器映射成 `invalid_args` |
| 黑雾单位归属漏掉全部单位 | `EnemyData.astroId` 与 `star.id` 不在同一编号域 | 按 `astroId` 反查天体再比 `star.index`；巢穴侧用 `hive.starData` |
| `FindPlanetByEnemy` 任何 id 都返回同一颗星球 | 循环里根本没用 `enemyId`，只要有敌人就返回 | 按 id 精确匹配 |
| `itemFilter` 解析后从未生效 | 只写进 request，没有任何过滤点用它 | 按名字或 id 过滤，`display`/`total`/`truncated` 同步 |
| 站点名下的无人机/运输船永远枚举不到 | 拿 `stationId`（组件下标）比 `station.entityId`（建筑实体 id） | 先换算成实体 id |
| 发射井返回全星系火箭 | 完全没用 `siloId`；`DysonRocket` 只带 `planetId` | 按发射行星归属，同星球多井无法区分 |
| 战斗基地返回全行星单位 | `UnitComponent` 无归属字段，归属在 `craft.owner` | 经 `craftId` 反查 owner |
| 地面黑雾基地的区域成员永远为空 | 敌人 id 与 `dfGBaseId` 是两套编号 | 先换算成基地组件 id |
| `FindPlanetByEnemy` 任何 id 都指向同一颗星球 | 循环里没用 `enemyId` | 按 id 精确匹配 |
| 戴森球层统计把已删除的层也算进去 | `layersIdBased` 按 id 索引、id 不连续，却用 `layerCount` 当上界 | 改用 `LayerExist` |
| 工厂连通分量可能吃到拆除前的旧结果 | 缓存只比 `entityCursor`，拆除后重建时不变 | 加连接池引用 + 16 位 protoId 抽查指纹 |

## 7. 分期

### P0：几何基础 + 行星区域

范围：

- `SpatialValue` / `Region` / `Point` 描述与校验。
- `system` / `star` / `planet` / `planet_patch` / `world_box` / `sphere`。
- `surface` / `universe` / `building` / `vein` / `vegetation` / `trash` / `celestial` 点。
- `resolve` / `at` / `frame` / `convert` / `project` / `describe` / `bbox`。
- `contains` / `distance`（点-点、点-几何）/ `members` / `count` / `stats`（行星/区域/盒/球）。
- `space_region` / `space_point` 两个工具。
- `game_analyze_area`、`game_capture_view`、`game_tether_add` 接受 `region` / `point`。

验收：

- 给定经纬度点，`planet_patch.contains` 在边界、跨 ±180°、极点、`alt>0` 四类用例正确。
- `point.building` / `point.vein` / `point.vegetation` / `point.trash` 能按 id 定位，拆除/采集/清除后返回 `stale`。
- `point.trash` 的 `frame` 与 `TrashData` 的 `uPos` / `lPos` 一致；不把漂移中的垃圾块当固定坐标。
- `region.members(planet, filter={kind:"vein"})` 与 `game_get_planet` 的矿脉节点一致。
- `region.members(planet)` 数量与 `game_get_entities` 一致（同过滤条件）。
- `region.stats(planet)` 与 `game_analyze_area(all=true)` 的配方/功率口径一致。
- `game_analyze_area(region=patch)` 与手工按经纬度过滤的结果一致。
- 现有工具不传新参数时行为不变。

### P1：电网/工厂 + 区域归属 + 命名变量

范围：

- `grid` / `factory`；`region.of(entity)`；`subregions(planet)`。
- `nearestMember` / `locate` / `distance`（集合）。
- `space_var`；`game_get_entities` / `game_render_layout` / `game_copy_blueprint` 接受 `region`。
- 工厂缓存与失效。

验收：

- 从种子建筑反推的工厂成员，与 `game_trace_line` 的节点集合一致（排除深度截断）。
- 一个跨两片电网的连通群，得到两个 `factory`，成员各自只含本电网部分。
- 电网成员包含一个「在覆盖半径内但不耗电」的传送带/建筑；与游戏 UI 对照。
- `region.of(building)` 返回 `factory → grid → planet → system` 的合理链。
- 拆除建筑后旧 `factory` 返回 `stale`，不返回错误成员。

### P2：物流/玩家动点 + 附近/定位

范围：

- `motion.player` / `motion.constructionDrone` / `motion.deliveryDrone` / `motion.logisticsDrone` / `motion.logisticsShip` / `motion.dysonRocket` / `motion.trash` / `motion.celestial` / `motion.track`。
- `list` / `state` / `track` / `predict` / `eta` / `closest` / `path` / `lost`。
- `space_motion`；`region.around`；`locate`；`contains(r, m)`。
- track 分帧 job；可选环形缓冲。

验收：

- 玩家移动 5 秒，`track` 返回 51 个样本（6 tick 间隔），`pathLength` 与位移合理。
- `motion.list(kind="construction_drone", region=planet)` 返回的 craftId 都能用 `state` 取到位置。
- 配送/物流运输机的 `state.model=interpolated`，位置落在 `begin/end` 之间；不提供 `predict`。
- 星际物流运输船在 `warpState>0` 时 `predict` 返回 `unsupported`，`state` 仍可用。
- 小型运载火箭按 `starId` 枚举；到达节点后 `lost=true`。
- `motion.trash` 在太空段和落地段都能返回 `state`；不提供 `predict`；垃圾块被清除/落地后 `lost=true`。
- 对一个球体区域，`eta` 首次命中 tick 与逐 tick 采样误差 ≤ `intervalTicks`。
- `track` 期间主线程单帧阻塞 ≤ 50ms；不抢焦点、不注入输入。
- 目标卸载后 `lost=true`，返回最后已知位置，不换成玩家位置。
- 超出预测地平线返回 `unsupported`，不返回编造的时间。

### P3：黑雾/戴森球 + 高级几何

范围：

- `hive` / `df_base` / `dyson`；`members` / `stats` / `subregions`。
- `point.dfSpaceBuilding` / `point.dfGroundBuilding`。
- `motion.combatDrone` / `motion.warship` / `motion.dfSpaceUnit` / `motion.dfGroundUnit`；对应 `list` / `state` / `track` / `predict`。
- `contains` 对戴森壳用 `DysonShell.IsPointInShell`；对基地/巢穴用包围体并标 `approximate`。
- 行星区域的精确边界距离；`sphere` / `world_box` 布尔运算；`intersects` 的跨 ±180°/极点加固。
- 可选 `intercept` / `watch`。

验收：

- 戴森壳内外点判定与 `IsPointInShell` 一致。
- 黑雾基地成员/单位数与游戏面板一致（或明确列出差异）。
- 太空黑雾建筑按 `starId+hiveId+enemyId` 定位，随巢穴轨道移动；读档后旧 id 返回 `stale`。
- `motion.list(kind="combat_drone")` / `warship` / `df_*_unit` 能列出活跃目标；击杀/卸载后 `lost=true`。
- 区域相交/距离在跨 ±180°、极点用例正确；近似结果带 `method`。

## 9. 风险与待决

### 风险

1. **电网覆盖口径**：`PowerNodeComponent.coverRadius` 是否等于 UI 的「电网覆盖」需要实机核对；多层建筑/附加建筑可能要用 `GetObjectPosition`。如果对不上，先只做「有电力组件的成员」，把不耗电建筑标为 `partial`，不要猜。
2. **工厂计算成本**：全量并查集在超大工厂上可能到几十毫秒；必须缓存 + 上限。工厂身份会随建造/拆除变化，`componentKey` 不能当永久 ID。
3. **预测时间基准**：`PredictUPose(double)` 的参数是秒还是 tick，必须用当前 `uPosition` 对照确认；错了会让所有未来时刻偏移。
4. **世界区域的未加载星球**：只能枚举已加载工厂；`partial=true` 必须被模型正确消费，否则会得出「盒子里没有建筑」的错误结论。
5. **动点预测的边界**：玩家/实体的路径不可预测；只能短时匀速。不要为了「好用」把 horizon 拉长。
6. **黑雾/戴森球的 API 面很大**：P3 前先做只读盘点，确认哪些池/字段稳定；不要先写一套完整战斗查询。
7. **Schema 复杂度**：10+1 种区域 union 会让工具 schema 变大；如果模型频繁传错，退化为「`type` + 扁平可选字段 + mod 严格校验」，并在提示词里给 3 个示例。

### 需要你确认

1. **世界区域的坐标系**：`world_box` 是银河系 AABB（恒星固定、行星穿过），还是某恒星系局部 AABB（跟着恒星走）？我建议前者；后者另加 `system_box`。
2. **两对容易混淆的目标**：
   - 「配送运输机」是玩家配送/补给的 courier，还是站点物流无人机？
   - 「战斗无人机」是地面 `CombatGroundSystem.units`，「战舰」是太空 `CombatSpaceSystem.fleets`，这样分对吗？
   这两对直接决定 `delivery_drone` / `logistics_drone` / `combat_drone` / `warship` 的数据源。
3. **分阶段优先级**：P2 先做玩家/建设无人机/配送/物流/运输船/火箭，P3 再做战斗无人机/战舰/黑雾单位，是否可接受？如果你更想先做黑雾，P3 可以提前。
4. **太空黑雾建筑的运动**：它随巢穴轨道运动，我叫它「定点」只是沿用表里的分类；查询时仍按 `t` 求值。这样理解对吗？
5. **垃圾块放哪**：我建议移到动点页，`归属=无`；`point.trash` 只做快照，`motion.trash` 做 `state` / `track`，不提供 `predict`。如果你更想保留在定点页，我就把它定义成「快照」，并在动点页加一个自由体备注；你选哪种？
6. **天体中心**：表里没有「行星/恒星中心」这一类，但 `sphere` / `eta` 需要一个中心点。我把它作为 `celestial` 扩展保留，是否合适？
7. **命名变量**：是否需要跨回合保存「那片产线」这类名字？作用域是会话还是存档？我建议会话，读档即失效运行期引用。
8. **几何精度**：行星区域的边界距离、区域相交是否需要精确球面解？我建议 P0 只做包含，P1 再做近似距离并标 `method`；布尔运算只支持球/盒。

### 表格建议再加三列

- 两页都加 `归属`：决定解析路径和生命周期；没有归属的只有玩家、垃圾块、未来的投射物/碎片。
- 「定点」页加 `id 来源`：`entityId` / `veinId` / `vegeId` / `enemyId`；这几类 id 不通用，模型很容易混。
- 「动点」页加 `可预测性`：`精确` / `插值` / `仅 track`；对应 `model` 字段，避免模型把插值位置当成精确物理位置。
- 「区域」页的恒星系、恒星、行星三列目前 `定义` 为空；可以补成：恒星系 = 以恒星为中心、`systemRadius` 为半径的范围；恒星 = 恒星本体；行星 = 行星本体 + 大气层。

> 如果按建议把垃圾块移到动点页：定点 7 行、动点 11 行；当前表是 8 / 10。两页的**列**不变，只多一列 `归属`。

**一句话总结**：把「区域、定点、动点」从三个名词变成一套带锚、带帧、带时刻的空间值；区域按 Area/Collection 能力分派；方法先做构造/包含/距离/成员/统计，再接动点采样与预测；行动复用现有工具而不是再造一套。
